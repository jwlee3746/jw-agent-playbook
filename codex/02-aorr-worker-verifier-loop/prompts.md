# 단계별 프롬프트 골격

각 단계에 넘기는 지시문의 뼈대다. `<...>` 자리를 채워 쓴다. [README](README.md)의 Phase 구분을 따른다.

## 모든 단계에 공통인 골격

```
[<단계 번호> - <단계 이름>]

<읽을 것: 상태 파일, 앞 단계 산출물, 현재 코드, Git 상태>

역할:
- Worker(<하네스>): <담당>
- Verifier(<하네스>): <담당>
- <한쪽을 쓸 수 없을 때의 fallback 조건>

실행 순서:
1. ...
2. ...

규칙:
- <금지 사항>

최종 보고:
- <무엇을 보고할지>

<이 단계에서 하지 말 것>
```

여섯 칸 중 **맨 앞과 맨 뒤가 자주 빠진다.** 무엇을 읽고 시작할지 없으면 에이전트가 컨텍스트에 남은 것만 보고 판단하고, 하지 말 것이 없으면 설계 단계에서 코드를 고치기 시작한다.

# Phase A · 설계

## 1. 업무 분석

```
[1 - 업무 분석]

<프로젝트 설정>을 상태 파일의 Project Settings에 기록해.
상태 파일이 없으면 해당 섹션만 생성해.
인증 정보는 값을 읽거나 저장하지 말고 파일명만 기록해.

<하려는 일 한 문단>

업무를 작은 개발 루프로 나누고 다음 표로 정리해:
루프 | 입력 | Act | Observe | 통과 기준 | 위험도 | HITL | 첫 루프 적합성

가장 안전한 첫 루프를 하나 추천해.
확인되지 않은 내용은 [사람 확인 필요]로 표시하고 추정하지 마.

결과를 <분석 문서>에 저장하고 핵심만 보고해.

코드 수정, 테스트, push, 배포는 하지 마.
```

## 2. 상태 머신 설계

```
[2 - 상태 머신 설계]

상태 파일의 Project Settings, <분석 문서>, 저장소 구조를 읽고
실행 가능한 AORR 상태 머신을 설계해.

역할:
- Worker: 코드 분석과 최소 수정
- Verifier: 테스트 실행과 판정
- <fallback 조건>

최종 목표:
- <완료 상태를 항목으로>

<설계 문서>에 다음만 작성해:
1. Target과 완료 기준
2. Act: Worker가 수행할 최소 수정
3. Observe: Verifier가 실행할 테스트와 수집할 결과
4. Reason: 실패 원인 분류
5. Repeat: 최소 수정 → 동일 테스트 재실행
6. Stop과 HITL 조건
7. 개발 루프 표: 루프 | 입력 | Act | Verify | 통과 기준 | 다음 상태

상태:
READY, ACTING, VERIFYING, RETRYING, PASSED,
DEPLOY_APPROVAL_REQUIRED, DEPLOYED, BLOCKED, HITL_REQUIRED

실패 분류:
<도메인 계열 분류들>, TEST, ENVIRONMENT, DEPLOYMENT, UNKNOWN

규칙:
- 한 Retry에서는 원인 하나와 관련 파일만 수정
- Verifier의 전체 검증이 통과해야 PASSED
- Verifier를 쓸 수 없으면 그 사실과 이유를 기록
- 불명확한 내용은 [사람 확인 필요]

아직 코드 수정, 테스트, push, 배포는 하지 마.
```

## 3. 검증 루프 설계

```
[3 - Self-Correcting TDD 설계]

상태 파일, <설계 문서>, 저장소 구조를 읽고
Verifier 중심 자기수정 루프를 설계해.

먼저 확인할 것:
1. Verifier 명령 사용 가능 여부
2. 로그인 및 실행 가능 여부
3. 사용 가능한 모델
4. 실제 모델명을 <설계 문서>와 상태 파일에 기록

<설계 문서>에 검증 루프를 추가해.

실행 순서:
1. Verifier가 변경 전 테스트 실행
2. Verifier가 실패 항목·핵심 오류·관련 파일·fingerprint 보고
3. Worker가 원인 하나에 필요한 최소 코드만 수정
4. Worker는 테스트를 실행하지 않고 재검증 요청
5. Verifier가 동일 테스트 재실행
6. 전체 테스트가 통과해야 PASSED

검증 범위:
- <정적 검사 항목>
- <실제 실행 검사 항목>
- <비밀정보 유출 검사>

실패 기록:
실행 주체 | 모델 | 명령 | exit code | 핵심 오류 | 관련 파일·라인 | fingerprint | 최종 상태

Retry:
- 오류당 최대 <N>회
- 동일 fingerprint <N>회면 중지
- 한 Retry에서는 원인 하나와 최소 파일만
- 테스트 삭제·완화 금지

이 단계에서는 코드 수정, 테스트 실행, push, 배포를 하지 마.
```

**3번의 "먼저 확인할 것"을 건너뛰지 않는다.** Verifier가 실제로 도는지 여기서 확인하지 않으면 Phase B에서 fallback으로 떨어지고, 그 구간의 통과 판정은 신뢰할 수 없게 된다.

## 4. 상태 파일 완성

```
[4 - 상태 파일 작성]

앞 단계에서 만든 상태 파일과 <설계 문서>를 읽고,
Project Settings를 보존하면서 복구용 상태 파일을 완성해.

구성: <MEMORY-template.md의 섹션 목록>

길이 규칙:
- 항목당 한 줄
- 원시 로그, 전체 명령 출력, diff, 코드 블록 저장 금지
- 같은 섹션을 반복 추가하지 말고 현재 상태를 갱신
- Project Settings를 중복 생성하거나 임의로 바꾸지 않기
- Recent Loops는 최근 3개만
- 상세 실행 기록은 <로그 파일>에 저장

Guardrails:
- <금지 사항 목록>

아직 코드 수정, 테스트, push, 배포는 하지 마.
```

# Phase B · 첫 루프 정확히 1회

```
[5 - 첫 개발 루프 정확히 1회 실행]

상태 파일, <분석 문서>, <설계 문서>와 기존 파일을 읽고
가장 안전한 첫 개발 루프를 정확히 1회 실행해.

역할:
- Verifier: 변경 전·후 테스트
- Worker: 테스트 결과에 따른 최소 코드 수정
- <fallback 조건>

실행 순서:
1. 상태 파일과 Git 상태 확인
2. Verifier와 모델 확인
3. Verifier가 변경 전 테스트 실행
4. 이번 루프의 최소 완료 기준 하나 확정
5. Worker가 필요한 최소 파일만 생성 또는 수정
6. Verifier가 동일 테스트 재실행
7. 결과를 상태 파일과 <로그 파일>에 기록
8. 정확히 한 번의 Act 후 중지

제한:
- 검증 실패 후 두 번째 수정은 하지 마
- 실패 시 RETRYING 또는 HITL_REQUIRED로 기록
- push와 배포 금지
- 상태 파일에는 한 줄 요약만, 상세는 <로그 파일>에

최종 보고:
- 실행 모드와 모델
- 선택한 루프
- 변경 파일
- 변경 전·후 테스트 결과
- 현재 상태
- 다음 작업
```

# Phase C · 전체 구현과 배포

```
[6 - 전체 구현과 최초 배포]

상태 파일, <분석 문서>, <설계 문서>와 기존 코드를 읽고
작은 루프를 순서대로 실행해 전체를 완성해.

먼저:
1. Verifier 실행 가능 여부와 모델 확인
2. 실제 모델명과 실행 모드를 상태 파일에 기록

필수 범위:
- <완료해야 할 기능 목록>
- <검증할 환경·조건>

각 루프:
1. Verifier가 변경 전 테스트
2. Worker가 원인 하나를 최소 수정
3. Verifier가 동일 테스트 재실행
4. 실패 시 Verifier가 오류와 fingerprint 보고
5. Worker가 최소 Retry
6. Verifier가 다시 검증
7. 전체 검증 통과 시 다음 루프로 이동

Retry:
- 오류당 최대 <N>회, 동일 fingerprint <N>회면 중지
- 한 Retry에서는 원인 하나와 최소 파일만
- 테스트 삭제·완화 금지

기타 규칙:
- 기존 콘텐츠 보존
- 확인되지 않은 정보는 [사람 확인 필요]
- 상태 파일은 <N>줄 이내, 상세 로그는 <로그 파일>
- 미완성 기능이 있으면 PASSED 처리 금지

모든 로컬 검증이 통과하면:
- 상태를 DEPLOY_APPROVAL_REQUIRED로 설정
- 대상, 변경 내용, 예상 URL을 보여주고 중지
- 사용자 승인 전에는 commit, push, 배포 금지

사용자 승인 후:
1. 비밀정보 추적 여부 확인
2. commit과 push
3. 배포
4. 응답 확인
5. Verifier가 배포본 회귀 테스트
6. 통과 시 DEPLOYED
```

배포 시 **상태 파일·실행 로그·인증 파일은 배포 대상에서 제외**한다고 명시한다.

- 사용자 승인 전 commit, push, 재배포 금지

사용자 승인 후:
1. 비밀정보 확인
2. commit과 push
3. 재배포
4. 응답 확인
5. Verifier가 배포본 회귀 테스트
6. DEPLOYED, BLOCKED 또는 HITL_REQUIRED 기록

## 반복되는 문구와 그 이유

여러 단계에 같은 문장이 계속 나온다. 각각이 막는 것이 다르다.

| 문구 | 막는 것 |
|---|---|
| "이 단계에서는 코드 수정·테스트·push·배포를 하지 마" | 설계 단계에서 구현이 시작되는 것 |
| "확인되지 않은 내용은 `[사람 확인 필요]`" | 지어낸 사실이 이후 모든 루프에 퍼지는 것 |
| "한 Retry에서는 원인 하나와 최소 파일만" | 무엇이 고쳤는지 귀속되지 않는 것 |
| "테스트 삭제·완화 금지, 기능 제거로 우회 금지" | 통과의 의미가 사라지는 것 |
| "Worker는 Verifier가 실행한 테스트를 중복 실행하지 않음" | 판정 주체가 둘이 되는 것 |
| "사용자 승인 전에는 commit·push·배포 금지" | 되돌리기 어려운 행위가 자동으로 일어나는 것 |
| "force push, hard reset, 기록 재작성 금지" | 무엇이 언제 잘못됐는지 추적 불가능해지는 것 |
| "인증 정보는 파일명만 기록, 값은 읽지도 저장하지도 않음" | 비밀정보가 로그·문서·Git에 남는 것 |
