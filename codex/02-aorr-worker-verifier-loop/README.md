# 02 · AORR Worker/Verifier 루프

Codex가 고치고 Claude가 검증한다. 실패 원인 하나에 최소 수정 하나로 대응하고, 같은 실패가 반복되면 멈춘다.

[01](../01-worktree-role-orchestration/)과 축이 다르다. 01은 **공간**을 나눠(worktree) 여러 역할을 동시에 돌리고, 이 항목은 **시간**을 나눠(상태 머신) 한 작업을 반복해서 수렴시킨다. 공유하는 것은 하나 — 만든 쪽이 통과 판정을 내리지 않는다.

## 언제 쓰나

목표가 하나로 뚜렷하고, **통과/실패를 기계가 말해줄 수 있는 작업**에 쓴다. 테스트가 있고, 실패하면 다시 돌리면 되는 일이다.

쓰면 안 되는 경우: 검증 세트를 만들 수 없을 때. 루프의 모든 판단이 검증 결과에 걸려 있어서, 판정이 없으면 에이전트가 자기 판단만 믿고 도는 구조가 된다.

## AORR

**Act → Observe → Reason → Repeat.** 코드를 고치고 → 테스트와 로그를 보고 → 실패 원인이 어디인지 판단하고 → 작은 수정으로 다시 돈다.

핵심은 **Act와 Observe를 다른 주체가 맡는다**는 것이다. Worker는 고치기만 하고 테스트를 돌리지 않는다. Verifier는 검증만 하고 코드를 고치지 않는다.

```
READY ──> ACTING ──> VERIFYING ──> PASSED ──> APPROVAL_REQUIRED ──> DONE
            ^            │
            └─ RETRYING ─┘  (실패 시)

어느 상태에서든 ──> HITL_REQUIRED   (사람 판단 필요)
                └─> BLOCKED         (환경·권한 장애, 안전한 대안 없음)
```

| 역할 | 담당 | 금지 |
|---|---|---|
| **Worker** (Codex) | 원인 하나에 대한 최소 수정 | 테스트 실행, 통과 판정 |
| **Verifier** (Claude) | 매번 동일한 전체 검증 세트 실행, 결과 보고 | 코드 수정 |
| **사람** | 배포·공개 범위·보안 판단, 최종 승인 | — |

---

# Step 1 · 작업대 정의

루프를 돌리기 전에 경계를 고정한다. 다섯 가지다.

- **저장소** — 어디서 작업하는가
- **읽고 쓸 수 있는 파일 범위** — 어디까지 손대도 되는가
- **실행 가능한 테스트 명령** — 무엇으로 판정하는가
- **로그와 결과 저장 위치** — 증거를 어디에 남기는가
- **정지 조건** — 언제 멈추고 사람을 부르는가

정지 조건이 가장 자주 빠진다. 없으면 무한 재시도로 간다.

> **흔한 실패** — "알아서 고쳐줘"로 시작한다. 범위·판정·정지가 전부 비어 있어 루프가 수렴하지 않는다.

---

# Step 2 · MEMORY.md와 규칙 파일 만들기

컨텍스트가 길어지면 에이전트는 이전 결정을 잊고, 금지한 변경을 다시 시도하고, 같은 실패를 반복한다. **세션이 리셋돼도 복구할 수 있는 기준점**을 파일로 둔다.

두 파일의 역할이 다르다.

| 파일 | 담는 것 | 성격 |
|---|---|---|
| `CLAUDE.md` / `AGENTS.md` | 프로젝트 규칙, 컨벤션, 테스트 실행 방법, 금지 작업 | 잘 안 바뀜 |
| `MEMORY.md` | 현재 목표·범위, 실패 이력, 수정 이력, 남은 확인 사항, Retry/Stop/HITL 조건 | 루프마다 갱신 |

## MEMORY.md 골격

```markdown
# MEMORY

## Project Settings
- <배포 주소, 저장소, 참고 자료, 비밀 파일 취급 규칙>

## Goal
- <한 문장>

## Scope / Out of Scope
- Scope: <포함>
- Out of Scope: <명시적 제외 — 이게 없으면 범위가 계속 넓어진다>

## Execution
- Mode: <Worker/Verifier 구성과 모델>
- 마지막 정상 commit·URL: <되돌아갈 지점>
- Rollback 기준: <force push·hard reset 금지 등>
- Last test: <결과 요약>

## Current State
- 상태: <상태 머신의 현재 값>
- 완료 루프 / 다음 루프:
- Retry: <횟수와 각 원인>
- fingerprint: <현재 실패 지문>
- blocker:

## Acceptance
- <완료로 인정하는 조건>

## Guardrails
- <테스트 삭제·완화 금지, 비밀정보 출력·커밋 금지, 임의 대규모 재작성 금지>

## Retry / HITL
- <최대 횟수, 중단 규칙, 사람에게 넘기는 조건>

## Recent Loops
| Loop | 상태 | 실행 모드·모델 | 변경 파일 | 테스트 결과 | Retry | 다음 작업 |
```

`Out of Scope`와 `Guardrails`가 실제로 일하는 칸이다. 무엇을 하지 말라고 적어두지 않으면 루프가 돌수록 범위가 넓어진다.

> **흔한 실패** — 두 하네스 세션이 같은 `MEMORY.md`를 동시에 편집해 한쪽이 덮어써진다. 상태 파일은 한 번에 한 세션만 쓴다.

# Step 3 · 검증 세트 만들기

Verifier가 **매번 똑같이** 돌릴 세트를 먼저 만든다. 루프마다 검증 범위가 달라지면 통과의 의미가 사라진다.

세트에 넣을 것은 작업 성격을 따르되, 정적 검사와 실제 실행을 모두 넣는다. 문법 검사만으로는 런타임 오류가 안 잡히고, 실행 검사만으로는 비밀정보 누출 같은 게 안 잡힌다.

각 실행 기록에 남길 필드를 고정한다.

```
실행 주체 | 모델 | 명령 | exit code | 핵심 오류 | 관련 파일·라인 | fingerprint | 최종 상태
```

**fingerprint**가 이 설계의 장치다. 실패를 짧은 식별자(`HTML-MISSING-SITE-SHELL-v1` 같은 형태)로 찍어두면 같은 실패가 반복되는지 기계적으로 셀 수 있다. 없으면 "비슷한 오류"인지 사람이 매번 판단해야 한다.

```bash
# 검증 세트는 작업 전에 한 번 돌려 baseline을 만든다
<검증 명령>; echo "exit=$?"
```

> **흔한 실패** — 검증 하네스를 작업 저장소 안에 둬서 배포 산출물에 섞인다. 저장소 밖(스크래치패드)에 둔다.

---

# Step 4 · 루프 실행

## Worker — 고치기만 한다

1. 직전 Verifier 보고에서 **원인 하나**를 고른다
2. 그 원인에 직접 관련된 **최소 파일만** 수정한다
3. **테스트를 돌리지 않는다.** 상태를 `VERIFYING`으로 넘기고 Verifier에게 요청한다

한 Retry에서 원인 두 개를 동시에 건드리지 않는다. 고쳐졌는지 아닌지 귀속이 안 된다.

## Verifier — 판정만 한다

1. **이전과 동일한 전체 세트**를 실행한다. 부분 검증으로 `PASSED`를 주지 않는다
2. PASS/FAIL, 실패 재현 절차, 관련 파일, **추정 원인 하나**, fingerprint를 보고한다
3. **코드를 고치지 않는다**

Verifier를 쓸 수 없는 상황이면 Worker가 대신 검증하지 않는다. 원인과 함께 `BLOCKED` 또는 `HITL_REQUIRED`로 보고한다. 대신 검증하는 순간 Worker/Verifier 분리가 사라진다.

> **흔한 실패** — Worker가 "확인차" 테스트를 돌리고 그 결과로 통과를 선언한다. 그러면 Verifier는 장식이 된다.

---

# Step 5 · 실패 분류와 재시도

실패는 **정확히 하나**로 분류한다. 분류 체계는 작업에 맞게 정하되, 코드 계열과 비코드 계열을 반드시 나눈다.

| 계열 | 예 | 처리 |
|---|---|---|
| 코드 | 마크업, 스타일, 로직, 상태 | Worker가 최소 수정 |
| 콘텐츠 | 사실 확인, 공개 범위, 문구 | 사람 판단 |
| 검증 자체 | 테스트 절차·기대값의 문제 | 임의로 고치지 말고 보고 |
| 환경·권한·배포 | CLI, 의존성, 인증, 배포 설정 | 코드 추정보다 환경 복구를 먼저 |
| 원인 불명 | 증거 부족 | 임의 수정 금지, `HITL_REQUIRED` |

**비코드 계열을 코드로 우회하지 않는 것**이 요점이다. 환경 문제를 코드로 덮으면 원인이 남은 채 증상만 사라진다.

## Retry 정책

- 오류당 최대 N회 (실습 기준 6회)
- 한 Retry = 원인 하나 + 최소 파일
- **금지: 테스트 삭제, 기대값 완화, 검증 범위 축소**
- **같은 fingerprint가 N회 반복되면 추가 수정 없이 중지** → `BLOCKED` 또는 `HITL_REQUIRED`
- 다른 fingerprint가 나오면 이전 오류와 섞지 않고 새 기록으로 분리

> **흔한 실패** — 통과시키려고 기대값을 낮춘다. 이걸 막지 않으면 나머지 구조가 전부 무의미해진다.

# Step 6 · 정지와 사람 인계

## 정지 조건

| 상태 | 뜻 |
|---|---|
| `PASSED` | 전체 검증 통과. 구현 루프 종료 |
| `APPROVAL_REQUIRED` | 코드·검증은 끝났으나 배포 승인 전. **승인 전에는 push·배포하지 않는다** |
| `HITL_REQUIRED` | 비밀정보 노출, 공개 범위 이탈, 배포 승인처럼 사람 판단이 필요 |
| `BLOCKED` | 환경·권한·외부 장애로 진행 불가, 안전한 대안도 없음 |

## 사람이 확인하는 것

```bash
git diff --stat <기준>..<현재>
git log --oneline <기준>..<현재>
```

이 출력과 `MEMORY.md`의 `Recent Loops`, 검증 로그가 판단 재료다. 승인 후에만 push한다.

## 되돌리기

`MEMORY.md`에 마지막 정상 commit을 남겨두고, 문제가 생기면 그 지점과 비교해 원인별로 되돌린다. **force push, hard reset, 기록 재작성은 하지 않는다** — 무엇이 언제 잘못됐는지 추적할 수 없게 된다.

---

## 이 설계의 요점

1. **Worker와 Verifier를 다른 주체로 둔다.** 원안은 서로 다른 하네스를 교차 배치했다. 같은 모델이 자기 수정을 검증하면 같은 맹점을 공유한다.
2. **실패에 지문을 찍는다.** fingerprint가 있어야 "같은 실패가 반복 중"을 기계가 센다.
3. **상태를 파일에 남긴다.** 컨텍스트가 압축돼도 `MEMORY.md`에서 복구한다.
4. **정지 조건을 먼저 정한다.** 무한 재시도가 비용이 새는 가장 흔한 경로다.

1번은 [01](../01-worktree-role-orchestration/)의 "판정자와 구현자 분리"와 같은 원리다. 01은 역할을 공간으로 갈랐고, 여기서는 하네스로 갈랐다.

## 결과

개인 웹사이트를 대상으로 완주해 배포까지 갔다. 관찰한 것은 아래와 같다.

- **잘 된 점 — 수렴했다.** Retry 7회, 각각 다른 원인 하나씩(날짜 유실, 목차 수집 누락, 수식 문자 손상, 무효한 태그 중첩, id 누락, 델리미터 오버플로, 이미지 레이아웃 시프트)이었다. 같은 원인이 두 번 나오지 않았다는 것은 "원인 하나 + 최소 수정" 규칙이 실제로 지켜졌다는 뜻이다.
- **잘 된 점 — 최종 검증이 촘촘했다.** 로컬 100/100(정적 70 + 브라우저 30), 배포본 브라우저 29/29, 배포본 41개 파일이 로컬과 바이트 동일, 외부 요청 0건, 비밀정보 0건.
- **실패한 점 — 교차 검증 구성을 끝까지 유지하지 못했다.** 원안은 Codex(Worker) + Claude(Verifier)였으나 **Codex 토큰이 소진되어** Claude main agent(Worker) + Claude sub agent(Verifier)로 전환했다. 분리는 남았지만 서로 다른 모델로 교차 검증하는 이점은 잃었다. 같은 모델이 만든 맹점을 같은 모델이 잡아낼 수 있는지는 이 실행으로 답하지 못한다.
- **실패한 점 — 초기 Verifier가 죽었다.** 첫 루프들에서 Claude CLI 세션이 응답 없이 정지해(중단 시 exit code 1) 검증을 Codex가 대신 수행하는 fallback 모드로 돌았다. **Verifier 없이 도는 구간이 생기면 그 구간의 통과 판정은 신뢰도가 낮다.** 나중에 Claude 검증이 정상화된 뒤에야 제대로 된 판정이 나왔다.
- **실패한 점 — 상태 파일이 덮어써졌다.** 외부 Codex 세션이 `MEMORY.md`를 덮어쓴 이력이 있고, 배포 커밋 하나를 revert하기도 했다. 두 하네스를 동시에 열어두면 상태 파일과 저장소가 경합한다. **상태 파일은 한 번에 한 세션만 써야 한다.**
- **다음에 바꾼다면**: 토큰 예산을 Verifier 쪽에 먼저 배정한다. Worker가 멈추면 진행이 늦어질 뿐이지만, Verifier가 멈추면 판정 없이 도는 구간이 생겨 결과 자체를 믿을 수 없게 된다.
