# 02 · AORR Worker/Verifier 루프

Worker가 고치고 Verifier가 검증한다. 실패 원인 하나에 최소 수정 하나로 대응하고, 같은 실패가 반복되면 멈춘다.

[01](../01-worktree-role-orchestration/)과 축이 다르다. 01은 **공간**을 나눠(worktree) 여러 역할을 동시에 돌리고, 이 항목은 **시간**을 나눠(상태 머신) 한 작업을 반복해서 수렴시킨다. 공유하는 것은 하나 — 만든 쪽이 통과 판정을 내리지 않는다.

## 언제 쓰나

목표가 하나로 뚜렷하고, **통과/실패를 기계가 말해줄 수 있는 작업**에 쓴다.

쓰면 안 되는 경우: 검증 세트를 만들 수 없을 때. 루프의 모든 판단이 검증 결과에 걸려 있어서, 판정이 없으면 에이전트가 자기 판단만 믿고 도는 구조가 된다.

## 하네스와 루프

용어를 먼저 갈라둔다. 둘은 층위가 다르다.

```
LLM Agent = LLM + Harness
Harness   = 도구 + 환경 + 상태 + 검증 + 제어 구조
Loop      = 그 하네스 안에서 도는 반복·피드백·종료 로직
```

**하네스는 작업 환경 전체를 설계하는 것**이고, **루프는 그 환경 안에서 반복하고 수정하는 흐름을 설계하는 것**이다. 이 항목이 다루는 것은 후자다 — 무엇을 읽고 쓸 수 있는지, 어떤 명령으로 판정하는지, 몇 번까지 재시도하는지, 언제 멈추고 사람에게 넘기는지.

프롬프트가 사라지는 것은 아니다. **루프 안에서 한 번 실행되는 부품이 된다.** 그래서 답변이 좋은지만 보지 않고 반복해서 굴릴 수 있는지도 본다. 완료·실패·보류 상태가 분명해야 한다는 요구가 여기서 나온다.

## AORR

**Act → Observe → Reason → Repeat.** 고치고 → 테스트와 로그를 보고 → 실패 원인이 어디인지 판단하고 → 작은 수정으로 다시 돈다.

핵심은 **Act와 Observe를 다른 주체가 맡는다**는 것이다.

| 역할 | 담당 | 금지 |
|---|---|---|
| **Worker** | 원인 하나에 대한 최소 수정 | 테스트 실행, 통과 판정 |
| **Verifier** | 매번 동일한 전체 검증 세트 실행, 결과 보고 | 코드 수정 |
| **사람** | 배포·공개 범위·보안 판단, 최종 승인 | — |

원안은 Worker와 Verifier에 **서로 다른 하네스**를 배치한다(예: Codex Worker + Claude Verifier). 같은 모델이 자기 수정을 검증하면 같은 맹점을 공유하기 때문이다. 한쪽을 쓸 수 없을 때만 fallback으로 한 주체가 둘 다 맡되, **그 사실과 이유를 기록**한다. fallback 구간의 통과 판정은 신뢰도가 낮다는 것을 나중에 알 수 있어야 한다.

## 상태

```
READY ──> ACTING ──> VERIFYING ──> PASSED ──> DEPLOY_APPROVAL_REQUIRED ──> DEPLOYED
            ^            │
            └─ RETRYING ─┘  (검증 실패)

어느 상태에서든 ──> HITL_REQUIRED   (사람 판단 필요)
                └─> BLOCKED         (환경·권한 장애, 안전한 대안 없음)
```

# 전체 절차

네 단계로 나뉜다. **앞의 넷은 설계만 하고 코드를 건드리지 않는다.** 설계와 실행을 섞으면, 무엇을 만들지 정하기 전에 만들기 시작해서 루프가 수렴하지 않는다.

| Phase | 단계 | 코드 수정 |
|---|---|---|
| **A. 설계** | 1 업무 분석 → 2 상태 머신 → 3 검증 루프 → 4 상태 파일 | 하지 않음 |
| **B. 첫 루프** | 5 가장 안전한 루프 **정확히 1회** | 최소 |
| **C. 전체 구현** | 6 루프 반복 → 승인 → 배포 | 예 |
| **D. 변경 재루프** | 7 요청 분석 → 8 항목별 재루프 | 7은 분석만, 8은 구현 |

# Phase A · 설계

## 1. 업무 분석

작업을 **작은 개발 루프 단위로 쪼갠다.** 루프 하나는 완료 기준이 하나여야 한다.

각 루프를 표로 정리한다.

```
루프 | 입력 | Act | Observe | 통과 기준 | 위험도 | HITL 필요 | 첫 루프 적합성
```

그다음 **가장 안전한 첫 루프 하나를 고른다.** 실패해도 되돌리기 쉽고, 다른 루프의 전제가 되는 것이 좋다.

확인되지 않은 내용은 추정하지 말고 `[사람 확인 필요]`로 표시한다. 여기서 지어낸 사실은 이후 모든 루프에 퍼진다.

## 2. 상태 머신 설계

Phase A에서 정한 것을 상태 머신으로 고정한다. 문서에 담을 것은 일곱 가지다.

1. **Target과 완료 기준** — 무엇이 되면 끝인가
2. **Act** — Worker가 할 수 있는 수정의 범위
3. **Observe** — Verifier가 실행할 테스트와 수집할 결과
4. **Reason** — 실패 원인 분류 체계
5. **Repeat** — 재시도 규칙
6. **Stop과 HITL 조건** — 각 정지 상태의 의미
7. **개발 루프 표** — 루프별 입력 / Act / Verify / 통과 기준 / 다음 상태

### 실패 분류

실패는 **정확히 하나**로 분류한다. 분류 체계는 작업에 맞게 정하되, **도메인 계열과 비도메인 계열을 반드시 나눈다.**

| 계열 | 예 | 처리 |
|---|---|---|
| 도메인 | 작업 대상의 계층별 분류 (마크업 / 스타일 / 로직 / 기능 단위) | Worker가 최소 수정 |
| 콘텐츠 | 사실 확인, 공개 범위, 문구 | 사람 판단 |
| 검증 자체 | 테스트 절차·기대값의 문제 | 임의로 고치지 말고 보고 |
| 환경·권한·배포 | CLI, 의존성, 인증, 배포 설정 | 코드 추정보다 환경 복구를 먼저 |
| 원인 불명 | 증거 부족 | 임의 수정 금지, `HITL_REQUIRED` |

**비도메인 계열을 코드로 우회하지 않는 것**이 요점이다. 환경 문제를 코드로 덮으면 원인이 남은 채 증상만 사라진다.

## 3. 검증 루프 설계

먼저 **Verifier를 실제로 쓸 수 있는지 확인한다.** 명령이 있는지, 로그인이 되는지, 어떤 모델이 잡히는지 확인하고 **실제 모델명을 기록**한다. "쓸 수 있을 것이다"로 넘어가면 Phase B에서 fallback으로 떨어진다.

### 검증 세트

Verifier가 **매번 똑같이** 돌릴 세트를 고정한다. 루프마다 범위가 달라지면 통과의 의미가 사라진다. 정적 검사와 실제 실행을 모두 넣는다 — 문법 검사만으로는 런타임 오류가 안 잡히고, 실행 검사만으로는 비밀정보 누출 같은 게 안 잡힌다.

판정 근거는 모델의 자기 판단이 아니라 **돌려서 결과가 나오는 것**이어야 한다. 단위 테스트, 린터, 타입 체커, 빌드 명령, API 응답 검사가 여기 해당한다. 이런 게 하나도 없으면 이 설계를 쓸 수 없다.

### Verifier가 넘기는 것

실패했을 때 Verifier가 Worker에게 **무엇을 주는지**가 비용을 좌우한다.

- **주지 않는 것**: 전체 로그, 전체 코드베이스, 지금까지의 대화 기록
- **주는 것**: 핵심 오류, 관련 파일과 라인, 재현 절차, fingerprint

Worker는 원인 하나를 판단하고 최소 수정만 하면 되므로 그 이상이 필요 없다. 로그 전체를 매번 넘기면 컨텍스트가 실패 이력으로 차오르고, 뒤로 갈수록 판단이 흐려진다.

### 실패 기록 필드

```
실행 주체 | 모델 | 명령 | exit code | 핵심 오류 | 관련 파일·라인 | fingerprint | 최종 상태
```

**fingerprint**가 이 설계의 장치다. 실패를 짧은 식별자로 찍어두면 같은 실패가 반복되는지 기계적으로 셀 수 있다. 없으면 "비슷한 오류"인지 사람이 매번 판단해야 한다.

### 재시도 규칙

- 오류당 최대 N회
- 한 Retry = **원인 하나 + 최소 파일**
- **금지: 테스트 삭제, 기대값 완화, 검증 범위 축소, 기능 제거로 우회**
- 다른 fingerprint가 나오면 이전 오류와 섞지 않고 새 기록으로 분리

N은 작업 성격에 맞춘다. 짧은 루프는 2~3회, 원인이 여러 겹인 작업은 6회 정도.

### 중단 조건

재시도 상한만으로는 부족하다. **더 고쳐봐야 소용없다는 신호**가 다섯 가지 있고, 하나라도 걸리면 멈춘다.

| 신호 | 왜 멈추나 |
|---|---|
| 같은 fingerprint가 N회 반복 | 그 방향으로는 답이 없다 |
| 같은 검증이 연속으로 실패 | 위와 같음 |
| 총 수정 시도가 상한 초과 | 원인을 못 좁히고 있다 |
| **실패 원인이 스펙·권한·데이터 구조 판단으로 옮겨감** | 코드로 풀 문제가 아니다 |
| **관련 파일을 특정하지 못함** | 어디를 고칠지 모르는 채로 고치면 범위가 넓어진다 |

아래 둘이 자주 빠진다. 둘 다 재시도 횟수와 무관하게, **첫 번째 시도에서도 걸릴 수 있는** 조건이다.

멈춘 뒤에는 `BLOCKED` 또는 `HITL_REQUIRED`로 기록하고 다음 절차로 넘어간다.

### 막혔을 때 — 같은 대화를 끌고 가지 않는다

멈추기만 하고 재개 절차가 없으면 결국 같은 세션에서 계속 시도하게 된다. 그러면 컨텍스트가 실패 이력으로 오염되고, 뒤로 갈수록 판단이 나빠진다.

```
1. 멈춘다
2. 실패 로그를 20줄 이내로 요약한다
3. 원인 후보를 2~3개로 나눈다
4. task를 더 작게 다시 쓴다
5. 새 컨텍스트에서 다시 시작한다
```

**4번이 핵심이다.** 같은 task를 그대로 다시 던지면 같은 실패가 반복된다. 자동화를 여는 것은 더 많은 권한이 아니라 더 명확한 완료 기준이다.

## 4. 상태 파일 완성

컨텍스트가 길어지면 에이전트는 이전 결정을 잊고, 금지한 변경을 다시 시도하고, 같은 실패를 반복한다. **세션이 리셋돼도 복구할 수 있는 기준점**을 파일로 둔다.

두 파일의 역할이 다르다.

| 파일 | 담는 것 | 성격 |
|---|---|---|
| `CLAUDE.md` / `AGENTS.md` | 프로젝트 규칙, 컨벤션, 테스트 실행 방법, 금지 작업 | 잘 안 바뀜 |
| `MEMORY.md` | 현재 목표·범위, 상태, 실패 이력, Retry/Stop/HITL 조건 | 루프마다 갱신 |
| 실행 로그 | 루프별 상세 기록 | 계속 쌓임 |

골격은 [`MEMORY-template.md`](MEMORY-template.md)에 있다.

### 길이 규칙

상태 파일이 커지면 컨텍스트를 잡아먹어 원래 목적을 잃는다.

- **항목당 한 줄.** 원시 로그, 전체 명령 출력, diff, 코드 블록을 넣지 않는다
- 같은 섹션을 반복 추가하지 말고 **현재 상태를 갱신**한다
- 최근 루프는 **3개만** 유지한다
- 상세는 별도 실행 로그 파일로 보낸다
- 전체 60줄 안쪽을 목표로 한다

# Phase B · 첫 루프 정확히 1회

가장 안전한 루프 하나를 **딱 한 번만** 돌린다. 여기서 여러 번 돌리면 무엇이 통했는지 귀속되지 않는다.

```
1. 상태 파일과 Git 상태 확인
2. Verifier 사용 가능 여부와 모델 확인
3. Verifier가 변경 전 테스트 실행          ← baseline
4. 이번 루프의 최소 완료 기준 하나 확정
5. Worker가 필요한 최소 파일만 수정
6. Verifier가 동일 테스트 재실행
7. 결과를 상태 파일과 실행 로그에 기록
8. Act 한 번 후 중지
```

**검증 실패 후 두 번째 수정을 하지 않는다.** 실패면 `RETRYING` 또는 `HITL_REQUIRED`로 기록하고 멈춘다. 여기서 멈추는 이유는 설계가 실제로 도는지 먼저 확인하기 위해서다 — 루프 구조 자체가 틀렸는데 계속 돌리면 잘못된 구조로 코드가 쌓인다.

이 단계에서 push와 배포는 하지 않는다.

# Phase C · 전체 구현과 배포

Phase A에서 나눈 루프를 순서대로 돈다. 각 루프는 같은 사이클이다.

```
Verifier 변경 전 테스트
  → Worker가 원인 하나 최소 수정
  → Verifier가 동일 테스트 재실행
  → 실패 시 Verifier가 오류와 fingerprint 보고
  → Worker가 최소 Retry
  → 전체 검증 통과 시 다음 루프
```

**미완성 기능이 있으면 `PASSED`로 처리하지 않는다.**

## 승인 게이트

모든 로컬 검증이 통과하면 **거기서 멈춘다.**

1. 상태를 `DEPLOY_APPROVAL_REQUIRED`로 설정
2. 변경 내용, 대상 저장소, 예상 URL을 보여주고 **중지**
3. 사용자 승인 전에는 commit·push·배포 금지

승인 후에 진행한다.

```bash
# 1) 비밀정보가 추적 대상에 들어갔는지 먼저 확인
git status --short
git diff --cached --stat

# 2) commit과 push
git add <배포 대상 파일만>
git commit -m "..."
git push origin main

# 3) 배포 후 확인
curl -o /dev/null -s -w "%{http_code}\n" <배포 URL>
```

배포에서 **상태 파일·로그·비밀 파일은 제외**한다. 배포 후 Verifier가 배포본 회귀 테스트를 돌리고, 통과하면 `DEPLOYED`다.

# Phase D · 변경 요청 재루프

배포 후 수정 요청이 오면 처음부터 다시 하지 않고 같은 구조를 축소해서 돈다.

## 7. 요청 분석 (구현하지 않는다)

**요청 원문을 그대로 보존**하고, 원자적인 Change Item으로 나눈다.

```
ID | 원문 | 분류 | 현재/기대 동작 | 대상 파일 | 의존성 | 완료 기준 | 검증 | 회귀 테스트 | 위험도 | HITL
```

- 중복·충돌·모호성을 표시한다
- **의존성 순서를 정한다** — 이게 구현 순서가 된다
- 항목마다 **변경 전·후 검증과 회귀 테스트를 미리 정의**한다
- 문서 기반 요청은 파일에서 확인된 사실만 쓴다. 확인 안 되면 `[사람 확인 필요]`

원문을 보존하는 이유는, 요약하면 나중에 "이게 그 요청이 맞나"를 확인할 수 없기 때문이다.

## 8. 항목별 재루프

시작 전에 상태 파일에 기록한다.

- 실행 모드와 모델
- 현재 commit
- **마지막 정상 commit·URL** ← 되돌아갈 지점
- Git 상태
- Rollback 기준

각 Change Item을 의존성 순서대로 돌린다. 사이클은 Phase C와 같되, **관련 회귀 테스트를 함께 돌린다.**

- 승인 범위 밖 파일을 수정하지 않는다
- 문서에 없는 사실을 만들지 않는다
- **force push, hard reset, 기록 재작성 금지** — 무엇이 언제 잘못됐는지 추적할 수 없게 된다

전부 통과하면 다시 승인 게이트로 간다.

# 비용과 컨텍스트 통제

루프는 방치하면 비용이 새는 구조다. 실패할수록 더 돌고, 돌수록 컨텍스트가 커진다.

## 역할을 나누는 두 번째 이유

Worker와 Verifier를 가르는 근거는 정확성만이 아니다. **비용도 근거다.**

검증은 대부분 기계가 한다 — 테스트, 린터, 타입 체커, 빌드는 모델을 부르지 않는다. 여기서 나온 결과 중 **핵심만 추려** 모델에게 넘기면, 비싼 쪽은 판단에만 쓰인다.

| | 나쁜 방식 | 좋은 방식 |
|---|---|---|
| 판정 | 모델이 코드를 읽고 "맞는 것 같다" | 검증 명령의 exit code |
| 모델에 넘기는 것 | 전체 로그 + 전체 코드베이스 + 대화 기록 | 실패 요약 + 관련 코드 조각 |
| 반복 실패 | 계속 재시도 | 반복을 감지하고 호출을 멈춤 |

## 가드레일

숫자로 못박아둔다. 없으면 상한이 사실상 무한이 된다.

- **최대 재시도 횟수** — 오류당, 그리고 전체
- **최대 실행 시간** — 루프 하나가 물릴 수 있는 시간
- **최대 로그 입력량** — 모델에 넘기는 로그의 상한 (예: 20줄 요약)
- **고성능 모델 호출 횟수** — 어느 단계에서 몇 번까지
- **같은 실패 반복 시 호출 중단** — 위 [중단 조건](#중단-조건)이 걸리면 추가 호출을 하지 않는다

마지막 항목이 가장 크게 아낀다. 같은 fingerprint로 도는 루프는 토큰만 쓰고 결과를 바꾸지 못한다.

## 한계에 닿았을 때

조용히 멈추지 않는다. **상한에 도달한 사실 자체가 보고 대상이다.**

- 재시도 한계 도달 → 사람에게 알린다
- 어느 가드레일에 걸렸는지, 그때까지의 fingerprint 이력을 함께 남긴다
- 사람 승인 전에는 어떤 경우에도 코드를 반영하지 않는다

상태 파일의 `Retry`와 `blocker` 칸이 이 기록의 자리다.

---

## 이 설계의 요점

1. **Worker와 Verifier를 다른 주체로 둔다.** 원안은 서로 다른 하네스를 교차 배치했다. 같은 모델이 자기 수정을 검증하면 같은 맹점을 공유한다. 비용 면에서도 갈라두는 편이 낫다 — 기계가 판정하고 모델은 판단에만 쓴다.
2. **설계와 실행을 분리한다.** Phase A는 코드를 건드리지 않는다. 무엇을 만들지 정하기 전에 만들기 시작하면 루프가 수렴하지 않는다.
3. **실패에 지문을 찍는다.** fingerprint가 있어야 "같은 실패가 반복 중"을 기계가 센다.
4. **상태를 파일에 남기되 짧게 유지한다.** 컨텍스트가 압축돼도 복구되지만, 파일이 커지면 그 자체가 컨텍스트를 잡아먹는다.
5. **정지 조건을 먼저 정한다.** 무한 재시도가 비용이 새는 가장 흔한 경로다.

1번은 [01](../01-worktree-role-orchestration/)의 "판정자와 구현자 분리"와 같은 원리다. 01은 역할을 공간으로 갈랐고, 여기서는 하네스로 갈랐다.

## 결과

개인 웹사이트를 대상으로 Phase D까지 완주해 배포까지 갔다.

- **잘 된 점 — 수렴했다.** Retry 7회가 전부 서로 다른 원인이었다(날짜 유실, 목차 수집 누락, 수식 문자 손상, 무효한 태그 중첩, id 누락, 델리미터 오버플로, 이미지 레이아웃 시프트). 같은 원인이 두 번 나오지 않았다는 것은 "원인 하나 + 최소 수정" 규칙이 실제로 지켜졌다는 뜻이다.
- **잘 된 점 — 최종 검증이 촘촘했다.** 로컬 100/100(정적 70 + 브라우저 30), 배포본 브라우저 29/29, 배포본 41개 파일이 로컬과 바이트 동일, 외부 요청 0건, 비밀정보 0건.
- **실패한 점 — 교차 검증 구성을 끝까지 유지하지 못했다.** 원안은 Codex(Worker) + Claude(Verifier)였으나 **Codex 토큰이 소진되어** Claude main agent(Worker) + Claude sub agent(Verifier)로 전환했다. 분리는 남았지만 서로 다른 모델로 교차 검증하는 이점은 잃었다. 같은 모델이 만든 맹점을 같은 모델이 잡아낼 수 있는지는 이 실행으로 답하지 못한다.
- **실패한 점 — 초기 Verifier가 죽었다.** 첫 루프들에서 Claude CLI 세션이 응답 없이 정지해(중단 시 exit code 1) 검증을 Worker가 대신 수행하는 fallback으로 돌았다. **Verifier 없이 도는 구간이 생기면 그 구간의 통과 판정은 신뢰도가 낮다.** 나중에 Verifier가 정상화된 뒤에야 제대로 된 판정이 나왔다.
- **실패한 점 — 상태 파일이 덮어써졌다.** 다른 하네스 세션이 `MEMORY.md`를 덮어쓴 이력이 있고, 배포 커밋 하나를 revert하기도 했다. 두 하네스를 동시에 열어두면 상태 파일과 저장소가 경합한다. **상태 파일은 한 번에 한 세션만 써야 한다.**
- **다음에 바꾼다면**: 토큰 예산을 Verifier 쪽에 먼저 배정한다. Worker가 멈추면 진행이 늦어질 뿐이지만, Verifier가 멈추면 판정 없이 도는 구간이 생겨 결과 자체를 믿을 수 없게 된다.
