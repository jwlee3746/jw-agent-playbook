# 7 · 변경 요청 분석 — 예제

**가상 프로젝트**: [6단계 예제](06-build-deploy.example.md)에서 이어진다. 검색이 배포된 뒤 사용자가 수정을 요청했다.

## 프롬프트

```
[7 - 사용자 수정 요청 분석]

[사용자 수정 요청]
1. 검색 결과에 문서 제목만 나오는데, 어느 부분이 걸렸는지 본문 일부도 보여줬으면 해
2. 카테고리별로 좁혀서 검색하고 싶어
3. 결과가 너무 많이 나올 때가 있어서 좀 줄여줘
4. 모바일에서 검색창이 키보드에 가려

MEMORY.md, 배포된 사이트, 현재 코드, Git 상태, DESIGN.md,
마지막 정상 배포 commit·URL을 확인해.

이번 단계에서는 구현하거나 테스트하지 마.

요청 원문을 보존하고 원자적인 Change Item으로 나눠 CHANGES.md에 저장해.

표:
ID | 원문 | 분류 | 현재/기대 동작 | 대상 파일 | 의존성 |
완료 기준 | 검증 | 회귀 테스트 | 위험도 | HITL

분류:
INDEX, SEARCH, UI, PERFORMANCE, CONTENT,
DEPLOYMENT, SECURITY, UNKNOWN

규칙:
- 중복·충돌·모호성 표시
- 의존성 순서 결정
- 문서 기반 요청은 파일에서 확인된 사실만 사용
- 불확실한 내용은 [사람 확인 필요]
- Change Item마다 변경 전·후 테스트를 정의
- DESIGN.md에는 실행 순서만 간단히 추가

코드 수정, 테스트, commit, push, 배포는 금지해.
```

## 기대하는 산출물

| ID | 원문 | 분류 | 현재/기대 | 대상 파일 | 의존성 | 완료 기준 | 회귀 테스트 | 위험도 | HITL |
|---|---|---|---|---|---|---|---|---|---|
| CR-1 | 1번 | INDEX | 인덱스에 본문 발췌 없음 → 매칭 구간 발췌 저장 | build-index.mjs | 없음 | 인덱스 크기 2MB 이내 유지하며 발췌 포함 | 문서 200개, 기존 질의 12개 | 중간 | 아니오 |
| CR-2 | 1번 | UI | 결과에 제목만 → 발췌도 표시 | search.js, search.html | CR-1 | 발췌가 질의어 강조와 함께 표시 | 결과 이동 12개 | 낮음 | 아니오 |
| CR-3 | 2번 | INDEX | 인덱스에 카테고리 없음 → 카테고리 필드 추가 | build-index.mjs | 없음 | 문서 200개 모두 카테고리 보유 | 문서 수, 크기 | 낮음 | 아니오 |
| CR-4 | 2번 | SEARCH+UI | 필터 없음 → 카테고리 필터 | search.js, search.html | CR-3 | 필터별 결과가 해당 카테고리만 | 기존 질의 12개 | 중간 | 아니오 |
| CR-5 | 3번 | SEARCH | 상한 없음 → 결과 수 제한 | search.js | 없음 | **[사람 확인 필요]** 상한 값과 초과 시 처리(더보기/페이지) 미정 | 기존 질의 12개 | 낮음 | **예** |
| CR-6 | 4번 | UI | 모바일에서 입력창이 가려짐 → 가려지지 않음 | search.html, 스타일 | 없음 | 모바일 뷰포트에서 입력창이 보임 | 데스크톱 레이아웃 | 낮음 | 아니오 |

**충돌·주의 표시**

- CR-1과 CR-3이 같은 파일(`build-index.mjs`)을 건드리고 둘 다 인덱스 크기에 영향을 준다. **함께 크기 상한을 넘길 수 있으므로 CR-1 → CR-3 순으로 하고 각각 크기를 확인**한다.
- 요청 3번은 "결과가 많다"는 증상만 있고 원하는 동작이 없다. CR-5는 `[사람 확인 필요]`.
- 요청 4번은 재현 조건이 불명확하다. 어느 기기·브라우저인지 확인이 필요하나, 모바일 뷰포트에서 재현되면 진행 가능.

**실행 순서**: `CR-1 → CR-3 → CR-2 → CR-4 → CR-6` (CR-5는 확인 후 편입)

## 이 예제에서 눈여겨볼 것

- **요청 하나가 항목 둘로 갈렸다.** 1번은 인덱스 변경(CR-1)과 UI 변경(CR-2)으로 나뉘고 의존 관계가 있다. 원자적으로 쪼개지 않으면 한 Retry에서 두 계층을 동시에 건드리게 된다.
- **의존성이 실행 순서를 바꿨다.** 요청 순서는 1-2-3-4지만 실행은 CR-1 → CR-3 → CR-2 → CR-4다. 인덱스 변경을 먼저 몰아서 하면 UI 작업이 완성된 인덱스 위에서 한 번에 끝난다.
- **CR-5는 구현 항목이 아니라 질문이다.** "줄여줘"는 상한 값도, 초과 시 처리(잘라내기/더보기/페이지네이션)도 정하지 않았다. 여기서 숫자를 지어내면 그 숫자가 완료 기준이 되어버린다.
- **CR-1과 CR-3의 상호작용을 짚었다.** 개별로는 안전하지만 합치면 크기 상한을 넘길 수 있다. 항목별로만 보면 놓치는 종류의 위험이다.
