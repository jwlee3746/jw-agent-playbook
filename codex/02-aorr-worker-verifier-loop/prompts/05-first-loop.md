# 5 · 첫 루프 정확히 1회 — 템플릿

가장 안전한 루프 하나를 딱 한 번만 돌린다. 설계가 실제로 도는지 확인하는 단계다.

## 프롬프트

```
[5 - 첫 개발 루프 정확히 1회 실행]

상태 파일, <분석 문서>, <설계 문서>와 기존 파일을 읽고
가장 안전한 첫 개발 루프를 정확히 1회 실행해.

역할:
- Verifier(<하네스>): 변경 전·후 테스트
- Worker(<하네스>): 테스트 결과에 따른 최소 코드 수정
- <fallback 조건>

실행 순서:
1. 상태 파일과 Git 상태 확인
2. Verifier와 모델 확인
3. Verifier가 변경 전 테스트 실행
4. 이번 루프의 최소 완료 기준 하나 확정
5. Worker가 필요한 최소 파일만 생성 또는 수정
6. Verifier가 동일 테스트 재실행
7. 결과를 상태 파일과 <로그 파일>에 기록
8. 정확히 한 번의 Act 후 중지

제한:
- 검증 실패 후 두 번째 수정은 하지 마
- 실패 시 RETRYING 또는 HITL_REQUIRED로 기록
- push와 배포 금지
- 상태 파일에는 한 줄 요약만, 상세는 <로그 파일>에

최종 보고:
- 실행 모드와 모델
- 선택한 루프
- 변경 파일
- 변경 전·후 테스트 결과
- 현재 상태
- 다음 작업
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<분석 문서>` `<설계 문서>` | 1~3단계 산출물 |
| `<하네스>` | Worker와 Verifier에 각각 다른 것 |
| `<로그 파일>` | 상세 기록 위치 |

## 주의

**"정확히 한 번의 Act 후 중지"와 "두 번째 수정 금지"가 이 단계의 전부다.** 여기서 여러 번 돌리면 무엇이 통했는지 귀속되지 않고, 더 중요하게는 루프 구조 자체가 틀렸는지 알 수 없다. 잘못된 구조로 코드가 쌓이는 것이 가장 비싼 실패다.

3번의 **변경 전 테스트**를 건너뛰지 않는다. baseline 없이는 이번 수정이 무엇을 바꿨는지 말할 수 없다. 첫 루프라 대부분 FAIL로 나오는 것이 정상이다.

4번이 3번 뒤에 오는 이유가 있다. 변경 전 테스트 결과를 보고 나서 이번 루프의 완료 기준을 확정해야, 실제 상태와 동떨어진 기준을 세우지 않는다.
