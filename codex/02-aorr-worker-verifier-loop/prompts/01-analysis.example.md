# 1 · 업무 분석 — 예제

**가상 프로젝트**: 정적 문서 사이트(마크다운 → HTML 빌드, 페이지 약 200개)에 클라이언트 사이드 전문 검색을 추가한다. 백엔드 없이 정적 호스팅만 쓴다.

## 프롬프트

```
[1 - 업무 분석]

아래 프로젝트 설정을 상태 파일의 Project Settings에 기록해.
상태 파일이 없으면 해당 섹션만 생성해.
인증 정보는 값을 읽거나 저장하지 말고 파일명만 기록해.

- 저장소: docs-site (로컬 경로 ./docs-site)
- 배포: 정적 호스팅, 빌드 산출물은 dist/
- 인증 파일: deploy_token.txt
- 빌드 명령: npm run build
- 기존 검색: 없음

문서 사이트에 클라이언트 사이드 전문 검색을 추가하려고 해.
백엔드를 두지 않고 빌드 시점에 인덱스를 만들어 브라우저에서 검색한다.
검색 페이지에서 제목과 본문을 대상으로 검색하고, 결과에서 해당 문서로 이동할 수 있어야 해.
인덱스 파일 크기와 첫 화면 로드 시간이 나빠지면 안 돼.

업무를 작은 개발 루프로 나누고 다음 표로 정리해:
루프 | 입력 | Act | Observe | 통과 기준 | 위험도 | HITL | 첫 루프 적합성

가장 안전한 첫 루프를 하나 추천해.
확인되지 않은 내용은 [사람 확인 필요]로 표시하고 추정하지 마.

결과를 ANALYSIS.md에 저장하고 핵심만 보고해.

코드 수정, 테스트, push, 배포는 하지 마.
```

## 기대하는 산출물

`ANALYSIS.md`에 이런 표가 나오면 된다.

| 루프 | 입력 | Act | Observe | 통과 기준 | 위험도 | HITL | 첫 루프 적합성 |
|---|---|---|---|---|---|---|---|
| 1. 인덱스 생성 | 빌드 산출물 | 빌드 후 인덱스 JSON 생성 스크립트 | 인덱스 파일 존재·문서 수 일치·크기 | 200개 문서가 모두 인덱스에 있고 크기가 상한 이내 | 낮음 | 아니오 | **높음** |
| 2. 검색 페이지 | 인덱스 | 검색 UI와 조회 로직 | 질의별 결과 정확도, 콘솔 오류 | 지정한 질의 집합이 기대 문서를 반환 | 중간 | 아니오 | 중간 |
| 3. 결과 이동 | 검색 결과 | 결과 항목 링크 연결 | 링크 유효성, 앵커 동작 | 결과에서 해당 문서로 이동 | 낮음 | 아니오 | 중간 |
| 4. 로드 성능 | 전체 | 인덱스 지연 로드 | 첫 화면 로드 시간, 전송량 | 검색 미사용 시 인덱스를 받지 않음 | 중간 | 아니오 | 낮음 |
| 5. 배포 회귀 | 전체 | 없음 | 배포본에서 1~4 재확인 | 배포본에서 동일 결과 | 낮음 | **예** (배포 승인) | 낮음 |

추천 첫 루프: **1번**. 산출물이 파일 하나라 되돌리기 쉽고, 2~4번이 전부 이 인덱스에 의존한다.

## 이 예제에서 눈여겨볼 것

- **인덱스 크기 상한과 질의 집합은 아직 정해지지 않았다.** 좋은 응답이라면 여기에 `[사람 확인 필요]`가 붙는다. 숫자를 지어내면 이후 모든 루프가 그 숫자를 기준으로 판정하게 된다.
- 루프 5는 위험도가 낮지만 HITL이 필요하다. **위험도와 사람 개입 여부는 다른 축이다** — 배포는 위험해서가 아니라 되돌리기 어려워서 승인이 필요하다.
- 루프 1의 통과 기준이 "인덱스가 잘 만들어진다"가 아니라 "문서 수가 일치하고 크기가 상한 이내"다. 판정 가능한 형태로 적혀야 Verifier가 돌 수 있다.
