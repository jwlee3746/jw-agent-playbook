# 3 · 검증 루프 설계 — 템플릿

Verifier가 실제로 도는지 확인하고, 매번 똑같이 돌릴 검증 세트를 고정한다. 코드는 아직 건드리지 않는다.

## 프롬프트

```
[3 - Self-Correcting TDD 설계]

상태 파일, <설계 문서>, 저장소 구조를 읽고
Verifier 중심 자기수정 루프를 설계해.

먼저 확인할 것:
1. Verifier 명령 사용 가능 여부
2. 로그인 및 실행 가능 여부
3. 사용 가능한 모델
4. 실제 모델명을 <설계 문서>와 상태 파일에 기록

<설계 문서>에 검증 루프를 추가해.

실행 순서:
1. Verifier가 변경 전 테스트 실행
2. Verifier가 실패 항목·핵심 오류·관련 파일·fingerprint 보고
3. Worker가 원인 하나에 필요한 최소 코드만 수정
4. Worker는 테스트를 실행하지 않고 재검증 요청
5. Verifier가 동일 테스트 재실행
6. 전체 테스트가 통과해야 PASSED

검증 범위:
- <정적 검사 항목>
- <실제 실행 검사 항목>
- <비밀정보 유출 검사>

실패 기록:
실행 주체 | 모델 | 명령 | exit code | 핵심 오류 | 관련 파일·라인 | fingerprint | 최종 상태

Verifier가 Worker에게 넘기는 것:
- 핵심 오류, 관련 파일·라인, 재현 절차, fingerprint
- 전체 로그·전체 코드베이스·대화 기록은 넘기지 않는다
- 로그를 넘길 때는 <M>줄 이내로 요약한다

Retry:
- 오류당 최대 <N>회
- 한 Retry에서는 원인 하나와 최소 파일만
- 테스트 삭제·완화 금지

중단 조건 (하나라도 걸리면 멈춘다):
- 동일 fingerprint <N>회 반복
- 같은 검증이 연속 실패
- 총 수정 시도가 상한 초과
- 실패 원인이 스펙·권한·데이터 구조 판단으로 옮겨감
- 관련 파일을 특정하지 못함

중단 후 절차:
1. 실패 로그를 <M>줄 이내로 요약
2. 원인 후보를 2~3개로 나눔
3. task를 더 작게 다시 씀
4. 새 컨텍스트에서 재시작
같은 세션에서 계속 시도하지 않는다.

비용 가드레일:
- 최대 재시도 횟수, 최대 실행 시간, 최대 로그 입력량
- 고성능 모델 호출 횟수 제한
- 중단 조건에 걸리면 추가 모델 호출을 하지 않는다
- 한계 도달 시 사람에게 알리고, 어느 가드레일에 걸렸는지 기록

이 단계에서는 코드 수정, 테스트 실행, push, 배포를 하지 마.
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<설계 문서>` | 2단계 산출물. 여기에 절을 추가한다 |
| `<정적 검사 항목>` | 실행 없이 확인 가능한 것 — 파일 존재, 문법, 스키마, 참조 |
| `<실제 실행 검사 항목>` | 돌려봐야 아는 것 — 런타임 오류, 동작, 응답 |
| `<비밀정보 유출 검사>` | 인증 정보가 추적 대상에 들어갔는지 |
| `<N>` | 재시도 상한. 짧은 루프는 2~3, 원인이 여러 겹이면 6 정도 |
| `<M>` | 모델에 넘길 로그 요약의 줄 수 상한. 20줄 안팎 |

## 주의

**"먼저 확인할 것"을 건너뛰지 않는다.** Verifier가 실제로 도는지 여기서 확인하지 않으면 다음 단계에서 fallback으로 떨어지고, 그 구간의 통과 판정은 신뢰할 수 없게 된다. "쓸 수 있을 것이다"로 넘어가는 것이 가장 흔한 실수다.

**모델명을 추정해서 적지 않는다.** 실제로 잡힌 값을 기록해야 나중에 "어느 모델이 판정했는가"를 되짚을 수 있다.

정적 검사와 실행 검사를 모두 넣는다. 문법 검사만으로는 런타임 오류가 안 잡히고, 실행 검사만으로는 비밀정보 누출 같은 게 안 잡힌다.

**중단 조건 다섯 가지 중 뒤의 둘이 자주 빠진다.** "실패 원인이 스펙·권한·데이터 구조 판단으로 옮겨감"과 "관련 파일을 특정하지 못함"은 재시도 횟수와 무관하게 **첫 시도에서도 걸릴 수 있다.** 코드로 풀 문제가 아니거나 어디를 고칠지 모르는 상태인데, 이때 계속 돌리면 범위만 넓어진다.

**"Verifier가 넘기는 것"이 비용을 좌우한다.** 전체 로그를 매번 넘기면 컨텍스트가 실패 이력으로 차오르고 뒤로 갈수록 판단이 흐려진다. Worker는 원인 하나를 판단하고 최소 수정만 하면 되므로 그 이상이 필요 없다.
