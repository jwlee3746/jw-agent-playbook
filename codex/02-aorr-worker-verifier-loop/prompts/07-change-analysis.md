# 7 · 변경 요청 분석 — 템플릿

배포 후 들어온 수정 요청을 원자적 항목으로 쪼갠다. 구현하지 않는다.

## 프롬프트

```
[7 - 사용자 수정 요청 분석]

[사용자 수정 요청]
<요청 원문을 그대로 붙여넣는다>

상태 파일, 배포된 결과물, 현재 코드, Git 상태, <설계 문서>,
마지막 정상 배포 commit·URL과 참고 자료를 확인해.

이번 단계에서는 구현하거나 테스트하지 마.

요청 원문을 보존하고 원자적인 Change Item으로 나눠 <변경 요청 문서>에 저장해.

표:
ID | 원문 | 분류 | 현재/기대 동작 | 대상 파일 | 의존성 |
완료 기준 | 검증 | 회귀 테스트 | 위험도 | HITL

분류:
<도메인 계열 분류들>, DEPLOYMENT, SECURITY, UNKNOWN

규칙:
- 중복·충돌·모호성 표시
- 의존성 순서 결정
- 문서 기반 요청은 파일에서 확인된 사실만 사용
- 불확실한 내용은 [사람 확인 필요]
- Change Item마다 변경 전·후 테스트를 정의
- <설계 문서>에는 실행 순서만 간단히 추가

코드 수정, 테스트, commit, push, 배포는 금지해.
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<요청 원문>` | 사용자가 쓴 문장 그대로. 요약하지 않는다 |
| `<설계 문서>` | 2~3단계 산출물 |
| `<변경 요청 문서>` | Change Item을 저장할 파일명 |
| `<도메인 계열 분류들>` | 2단계에서 정한 것을 재사용 |

## 주의

**요청 원문을 보존한다.** 요약해서 옮기면 나중에 "이게 그 요청이 맞나"를 확인할 수 없다. 특히 요청이 여러 번 오간 경우, 원문이 있어야 어느 문장에서 나온 항목인지 되짚을 수 있다.

**의존성 순서가 이 단계의 산출물이다.** 이게 곧 다음 단계의 구현 순서가 된다. 순서를 정하지 않으면 나중 항목이 앞 항목을 되돌리는 일이 생긴다.

**항목마다 회귀 테스트를 미리 정의한다.** 배포된 것을 고치는 작업이라, 새 기능이 도는지보다 기존 것이 안 깨지는지가 중요하다.

`[사람 확인 필요]`가 붙은 항목은 다음 단계 전에 해소한다.
