# 3 · 검증 루프 설계 — 예제

**가상 프로젝트**: [2단계 예제](02-state-machine.example.md)에서 이어진다.

## 프롬프트

```
[3 - Self-Correcting TDD 설계]

상태 파일, DESIGN.md, 저장소 구조를 읽고
Verifier 중심 자기수정 루프를 설계해.

먼저 확인할 것:
1. claude 명령 사용 가능 여부
2. 로그인 및 실행 가능 여부
3. 사용 가능한 모델
4. 실제 모델명을 DESIGN.md와 상태 파일에 기록

DESIGN.md에 검증 루프를 추가해.

실행 순서:
1. Verifier가 변경 전 테스트 실행
2. Verifier가 실패 항목·핵심 오류·관련 파일·fingerprint 보고
3. Worker가 원인 하나에 필요한 최소 코드만 수정
4. Worker는 테스트를 실행하지 않고 재검증 요청
5. Verifier가 동일 테스트 재실행
6. 전체 테스트가 통과해야 PASSED

검증 범위:
- 인덱스 파일 존재, JSON 스키마, 문서 수 200개 일치, 파일 크기
- 빌드 명령 exit code, 빌드 산출물 경로
- 로컬 HTTP 서버에서 검색 페이지 응답, 브라우저 콘솔 오류
- 질의 집합 실행: 각 질의가 기대 문서를 반환하는지
- 결과 항목 링크의 유효성과 앵커 이동
- 검색 미사용 시 인덱스 파일이 전송되지 않는지 (네트워크 요청 목록)
- deploy_token.txt와 토큰 패턴이 Git 추적 대상·빌드 산출물에 없는지

실패 기록:
실행 주체 | 모델 | 명령 | exit code | 핵심 오류 | 관련 파일·라인 | fingerprint | 최종 상태

Retry:
- 오류당 최대 4회
- 동일 fingerprint 4회면 중지
- 한 Retry에서는 원인 하나와 최소 파일만
- 테스트 삭제·완화 금지

이 단계에서는 코드 수정, 테스트 실행, push, 배포를 하지 마.
```

## 기대하는 보고

"먼저 확인할 것"의 결과가 이런 형태로 나와야 한다.

```
Verifier 확인 결과
- claude 명령: 사용 가능 (/usr/local/bin/claude)
- 로그인: 정상
- 실행 확인: 단문 프롬프트 응답 성공
- 모델: <실제로 잡힌 모델 식별자>
- 기록 위치: DESIGN.md 3절, MEMORY.md Execution
```

확인이 실패했다면 이렇게 나와야 한다.

```
Verifier 확인 결과
- claude 명령: 사용 가능
- 로그인: 정상
- 실행 확인: 실패 — 응답 없이 정지, 중단 시 exit code 1
- 조치: Worker가 대신 검증하지 않는다.
  원인과 함께 BLOCKED로 보고하고 사람 판단을 기다린다.
```

## fingerprint 예시

이 프로젝트에서 나올 법한 지문들이다.

| fingerprint | 뜻 |
|---|---|
| `INDEX-DOC-COUNT-MISMATCH-v1` | 인덱스 문서 수가 200과 다름 |
| `SEARCH-QUERY-NO-HIT-v1` | 질의 집합 중 일부가 기대 문서를 못 찾음 |
| `PERF-INDEX-EAGER-LOAD-v1` | 검색 미사용인데 인덱스를 내려받음 |
| `ENV-LOCAL-SERVER-UNAVAILABLE-v1` | 로컬 서버가 뜨지 않음 |

**같은 증상이라도 원인이 다르면 다른 지문**이다. 지문이 같은데 4회 반복되면 그 방향으로는 더 고치지 않는다.

## 이 예제에서 눈여겨볼 것

- **검증 범위에 "미사용 시 인덱스가 전송되지 않는지"가 있다.** 성능 제약을 말이 아니라 관찰 가능한 신호(네트워크 요청 목록)로 바꿔놓았다. 이렇게 적지 않으면 판정할 수 없다.
- **Retry 상한이 4회다.** 이 작업은 원인 계층이 얕아서 6회까지 갈 일이 드물다. 상한은 작업 성격에 맞춘다.
- Verifier 확인이 실패했을 때의 조치가 "Worker가 대신 검증"이 아니라 `BLOCKED`다. 대신 검증하는 순간 Worker/Verifier 분리가 사라진다.
