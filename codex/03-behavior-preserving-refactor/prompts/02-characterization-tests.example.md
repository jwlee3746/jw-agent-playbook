1단계에서 나온 공백 6개를 덮는다.

## 프롬프트

```
[2 - 특성화 테스트]

계획 문서 docs/refactor-plan.md의 공백 목록을 읽어.

각 공백 경로에 대해 특성화 테스트를 작성해.
특성화 테스트는 코드가 "해야 하는 일"이 아니라
"지금 실제로 하는 일"을 기록하는 테스트다.

작성 규칙:
1. 기대값은 추론하지 말고 실제로 실행해서 나온 값을 쓴다.
   실행하지 않고 쓴 기대값은 코드가 아니라 네 예상을 고정하는 것이다.
2. 현재 동작이 버그로 보여도 고치지 마. 버그를 그대로 기록하고,
   테스트에 주석으로 [의심스러운 동작]이라고 표시한 뒤 별도로 보고해.
3. 다음 네 가지를 모두 고정해:
   - 반환값 (정상, 경계, 빈 입력)
   - 예외 (어떤 입력에 어떤 타입·메시지)
   - 부수효과 (호출된 외부 함수, 인자, 그리고 호출 순서)
   - 상태 변화 (호출 전후 객체 상태)
   특히 settle()과 cancel()은 외부 호출 순서를 반드시 단언해.
   vi.mock의 mock.invocationCallOrder를 써서 순서를 고정해.
4. 테스트 파일은 test/characterization/ 아래에 둔다.
5. 기존 테스트 파일은 수정하지 마. 새 파일로 추가해.

작성 후:
- 전체 테스트 실행: npx vitest run
- 커버리지 재측정: npx vitest run --coverage --coverage.reporter=text
- 공백 목록의 6개 항목이 덮였는지 하나씩 대조해서 보고해

덮지 못한 항목이 있으면 억지로 덮으려 하지 말고
그 항목과 이유를 보고해. 그 대상은 리팩토링 범위에서 뺀다.

프로덕션 코드는 한 줄도 수정하지 마.
테스트 작성을 위해 필요해 보여도 수정하지 말고 보고해.
```

### [의심스러운 동작] 보고

쿠폰 2장을 적용하면 두 번째 쿠폰이 **첫 쿠폰 적용 후 금액이 아니라 원래 금액에** 계산된다. 정률 쿠폰 2장(10% + 10%)에서 19%가 아니라 20%가 할인된다.

버그로 보이지만 고치지 않고 현재 동작으로 기록했다.

```ts

// 리팩토링 범위 밖. 별도 이슈로 남긴다.
expect(totals.discount).toBe(2000) // 10000 * 0.1 + 10000 * 0.1
```

### 덮지 못한 항목

`cancel()`의 `refund` 실패 후 롤백 경로(공백 6). `paymentGateway`가 생성자에서 직접 `new PaymentGateway()`로 만들어져 주입할 수 없다. 실패를 흉내 낼 방법이 없다.

프로덕션 코드를 고치면 덮을 수 있지만 이 단계에서는 금지되어 있으므로 보고만 한다. → **3단계 계획표에 "생성자 의존성 주입"을 첫 항목으로 넣을 것.**

`cancel()`은 그 항목이 끝나고 특성화 테스트를 보강하기 전까지 리팩토링 범위에서 뺀다.

## 이 예제에서 볼 것

**쿠폰 버그를 고치지 않은 것**이 이 단계의 핵심이다. 고쳤다면 이후 모든 리팩토링에서 `#recalcTotals()` 관련 테스트가 깨질 때마다 원인이 둘로 늘어난다.

**공백 6을 덮지 못한 채로 진행한 것**도 정상이다. 억지로 덮으려면 프로덕션 코드를 고쳐야 하고, 그러면 안전망 없이 코드를 바꾸는 셈이 된다. 순서를 지키면 — 의존성 주입을 계획표 첫 항목으로 넣고, 그 변경 자체는 기계적 갈래로 처리하고, 끝난 뒤 테스트를 보강하고, 그다음 `cancel()`을 리팩토링한다.

커버리지가 100%가 아니어도 된다. 남은 559-561은 범위에서 뺀 `exportOrderCsv()`다.
