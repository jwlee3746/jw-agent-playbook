# 1 · 범위와 진단 — 템플릿

리팩토링 대상을 심볼 단위로 확정하고, 지금 안전망이 어디까지 덮는지 **측정한다.** 코드는 건드리지 않는다.

## 프롬프트

```
[1 - 범위와 진단]

<프로젝트 설정>을 계획 문서의 Project Settings에 기록해.
계획 문서가 없으면 해당 섹션만 생성해.

리팩토링 대상 후보: <대상 범위>
리팩토링 동기: <왜 바꾸려는가>

1. 대상을 파일과 심볼 단위로 나열해. 모듈 이름이 아니라
   함수·클래스·메서드 단위로 적어.

2. 다음 명령을 실행해서 현재 안전망을 측정해:
   - 전체 테스트: <테스트 명령>
   - 커버리지: <커버리지 명령>
   측정 출력을 그대로 인용해. 코드를 읽고 추정하지 마.

3. 대상별로 다음 표를 만들어:
   심볼 | 라인 수 | 분기 수 | 덮인 분기 | 덮이지 않은 경로 | 외부 호출·부수효과

4. 덮이지 않은 경로를 공백 목록으로 따로 모아. 이게 2단계 입력이 된다.

5. 대상 중 이번 범위에서 빼야 할 것이 있으면 근거와 함께 말해.

확인되지 않은 내용은 [사람 확인 필요]로 표시하고 추정하지 마.
결과를 <계획 문서>에 저장하고 핵심만 보고해.

코드 수정, 테스트 추가, 커밋은 하지 마.
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<프로젝트 설정>` | 대상 저장소, 언어·런타임, 테스트 프레임워크, 사용 가능한 LSP·AST 도구 |
| `<대상 범위>` | 시작점. 파일 경로나 디렉토리. 여기서 심볼 단위로 좁히는 것이 이 단계의 일 |
| `<왜 바꾸려는가>` | 구체적으로. "지저분해서"가 아니라 "결제 로직을 바꿀 때마다 알림 테스트가 깨져서" |
| `<테스트 명령>` / `<커버리지 명령>` | 실제로 도는 명령. 없으면 이 설계를 쓸 수 없다 |
| `<계획 문서>` | 6단계까지 계속 갱신할 파일 |

## 주의

**라인 커버리지가 아니라 분기 커버리지를 본다.** 라인 90%는 `if` 한쪽만 타고도 나온다. 리팩토링이 깨뜨리는 것은 대개 안 타본 쪽이다.

`외부 호출·부수효과` 칸이 이 단계의 진짜 산출물이다. 2단계에서 무엇을 고정해야 하는지가 여기서 나오고, 이 칸이 비어 있으면 반환값만 고정한 얕은 테스트가 만들어진다.

동기를 구체적으로 쓰는 이유는 3단계 때문이다. "결제를 바꾸면 알림이 깨진다"는 동기가 있어야 어느 결합을 끊어야 하는지가 계획표에 반영된다.
