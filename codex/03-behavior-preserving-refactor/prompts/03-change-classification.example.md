# 3 · 분류와 계획 — 예제

## 프롬프트

```
[3 - 분류와 계획]

기준선:
- 안전망 커밋: a3f81c2
- 테스트 경로: test/ — 이 시점부터 동결. 읽기만 한다
- 전체 테스트 명령: npx vitest run

계획 문서 docs/refactor-plan.md의 대상 표와 리팩토링 동기를 읽어.

동기(결제·재고·알림이 한 클래스에 결합되어 한 책임만 떼어 바꿀 수 없다)를
해결하기 위해 필요한 변경을 모두 나열하고, 각각을 두 갈래 중 하나로 분류해:

[기계적] 도구가 정확하게 처리할 수 있는 변경
  - 심볼 이름 변경, 파일·심볼 이동, import 정리
  - 시그니처 파라미터 순서·타입 표기
  - 문법 현대화, 데드코드 제거
  → 사용할 도구와 명령을 함께 적어.
     쓸 수 있는 것: tsserver LSP rename, ts-morph 스크립트, eslint --fix
  → 도구로 처리할 수 없는 이유가 있으면 판단 갈래로 옮겨

[판단] 정답 도구가 없는 변경
  - 함수·클래스 분해, 책임 재배치
  - 중복 통합, 추상화 도입
  - 조건문·제어흐름 구조 변경
  → 국소 단위로 쪼개. 한 항목은 한 번에 검증 가능한 크기여야 한다
  → "OrderService를 분해한다"는 항목이 아니다

계획표로 정리해:
ID | 대상 심볼 | 갈래 | 변경 내용 | 의존성 | 되돌리기 단위 | 위험도 | 사람 리뷰

순서 규칙:
- 기계적 항목을 판단 항목보다 앞에 둔다
- 다른 항목의 전제가 되는 것을 앞에 둔다
- 의존성 순서가 곧 실행 순서다

각 항목에 대해 "이 변경이 깨뜨릴 수 있는 테스트"를 미리 적어.
적을 수 없으면 그 항목은 안전망이 부족한 것이므로 표시해.

2단계에서 보고된 미해결 항목(cancel()의 refund 실패 경로,
생성자 의존성 주입)을 계획에 반영해.

결과를 docs/refactor-plan.md에 저장하고 계획표를 보고해.

코드와 테스트를 수정하지 마. 이 단계는 계획만 세운다.
```

## 이 예제에서 볼 것

**T1이 테스트 동결의 명시적 예외**다. 2단계에서 덮지 못한 경로가 M1(의존성 주입)이 끝나면 덮을 수 있게 된다. 예외를 계획표에 항목으로 올려두면 "테스트를 왜 고쳤나"가 나중에 추적된다. 프롬프트로 금지한 것을 예외로 열 때는 **반드시 계획표에 남긴다.**

**M1을 기계적으로 분류한 것**이 판단이 갈릴 지점이다. 의존성 주입은 설계 변경처럼 들리지만, 여기서는 "생성자에서 `new`하던 것을 파라미터로 옮기고 모든 호출부를 갱신한다"로 형태가 정해져 있고 `ts-morph`가 호출부를 빠짐없이 처리한다. 정답이 하나면 기계적이다.

**J3과 J4의 위험도가 상**인 이유는 둘 다 `settle()`의 호출 순서를 건드리기 때문이다. 1단계에서 "이 순서"라고 적어둔 것이 여기까지 이어진다.

`OrderService`를 세 클래스로 쪼개는 일이 J1·J2·J3 세 항목으로 나뉜 것에 주목할 것. 한 항목으로 던지면 테스트가 깨졌을 때 셋 중 무엇이 원인인지 알 수 없다.
