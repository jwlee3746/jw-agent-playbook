# 2 · 특성화 테스트 — 템플릿

1단계의 공백 목록을 테스트로 덮는다. **옳은 동작이 아니라 현재 동작**을 고정한다. 프로덕션 코드는 건드리지 않는다.

## 프롬프트

```
[2 - 특성화 테스트]

계획 문서 <계획 문서>의 공백 목록을 읽어.

각 공백 경로에 대해 특성화 테스트를 작성해.
특성화 테스트는 코드가 "해야 하는 일"이 아니라
"지금 실제로 하는 일"을 기록하는 테스트다.

작성 규칙:
1. 기대값은 추론하지 말고 실제로 실행해서 나온 값을 쓴다.
   실행하지 않고 쓴 기대값은 코드가 아니라 네 예상을 고정하는 것이다.
2. 현재 동작이 버그로 보여도 고치지 마. 버그를 그대로 기록하고,
   테스트에 주석으로 [의심스러운 동작]이라고 표시한 뒤 별도로 보고해.
3. 다음 네 가지를 모두 고정해:
   - 반환값 (정상, 경계, 빈 입력)
   - 예외 (어떤 입력에 어떤 타입·메시지)
   - 부수효과 (호출된 외부 함수, 인자, 그리고 호출 순서)
   - 상태 변화 (호출 전후 객체 상태)
4. 테스트 파일은 <테스트 경로>에 둔다.
5. 기존 테스트 파일은 수정하지 마. 새 파일로 추가해.

작성 후:
- 전체 테스트 실행: <테스트 명령>
- 커버리지 재측정: <커버리지 명령>
- 공백 목록의 각 항목이 덮였는지 하나씩 대조해서 보고해

덮지 못한 항목이 있으면 억지로 덮으려 하지 말고
그 항목과 이유를 보고해. 그 대상은 리팩토링 범위에서 뺀다.

프로덕션 코드는 한 줄도 수정하지 마.
테스트 작성을 위해 필요해 보여도 수정하지 말고 보고해.
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<계획 문서>` | 1단계 산출물 |
| `<테스트 경로>` | 특성화 테스트를 모을 곳. 3단계 이후 동결 대상이 되므로 경로가 분명해야 한다 |
| `<테스트 명령>` / `<커버리지 명령>` | 1단계와 같은 명령 |

## 주의

**"실행해서 나온 값을 쓴다"가 이 단계의 전부다.** 에이전트는 코드를 읽고 기대값을 추론할 수 있고, 대개 그럴듯하게 맞춘다. 그런데 특성화 테스트가 잡아야 하는 것은 정확히 그 추론이 틀리는 지점 — 코드가 예상과 다르게 동작하는 곳이다.

버그를 고치지 말라는 규칙에 저항이 있을 수 있다. 이유는 단순하다. 리팩토링 중에 동작이 바뀌면 테스트가 깨졌을 때 **구조를 잘못 바꾼 것인지 버그를 고쳐서인지 구분할 수 없다.** 버그는 리팩토링이 끝난 뒤에 별도로 고친다. 그때는 구조가 나아져 있어서 고치기도 쉽다.

프로덕션 코드 수정 금지가 걸리는 경우가 있다 — 테스트하려면 의존성을 주입할 수 있어야 하는데 생성자에 하드코딩되어 있는 식이다. **이건 3단계 계획표의 항목**이지 여기서 몰래 할 일이 아니다. 보고하고 넘긴다.

## 이 단계가 끝나면

공백 목록이 비어야 한다. 그리고 **커밋한다.** 이 커밋이 이후 모든 되돌리기의 기준점(안전망 커밋)이 되므로 SHA를 계획 문서에 적어둔다.
