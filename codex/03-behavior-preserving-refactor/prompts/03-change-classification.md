# 3 · 분류와 계획 — 템플릿

바꿀 것을 **기계적 갈래와 판단 갈래로 가른다.** 계획만 세우고 아무것도 바꾸지 않는다.

## 프롬프트

```
[3 - 분류와 계획]

기준선:
- 안전망 커밋: <SHA>
- 테스트 경로: <테스트 경로> — 이 시점부터 동결. 읽기만 한다
- 전체 테스트 명령: <테스트 명령>

계획 문서 <계획 문서>의 대상 표와 리팩토링 동기를 읽어.

동기를 해결하기 위해 필요한 변경을 모두 나열하고,
각각을 두 갈래 중 하나로 분류해:

[기계적] 도구가 정확하게 처리할 수 있는 변경
  - 심볼 이름 변경, 파일·심볼 이동, import 정리
  - 시그니처 파라미터 순서·타입 표기
  - 문법 현대화, 데드코드 제거
  → 사용할 도구와 명령을 함께 적어. <사용 가능한 도구>
  → 도구로 처리할 수 없는 이유가 있으면 판단 갈래로 옮겨

[판단] 정답 도구가 없는 변경
  - 함수·클래스 분해, 책임 재배치
  - 중복 통합, 추상화 도입
  - 조건문·제어흐름 구조 변경
  → 국소 단위로 쪼개. 한 항목은 한 번에 검증 가능한 크기여야 한다
  → "OrderService를 분해한다"는 항목이 아니다

계획표로 정리해:
ID | 대상 심볼 | 갈래 | 변경 내용 | 의존성 | 되돌리기 단위 | 위험도 | 사람 리뷰

순서 규칙:
- 기계적 항목을 판단 항목보다 앞에 둔다
- 다른 항목의 전제가 되는 것을 앞에 둔다
- 의존성 순서가 곧 실행 순서다

각 항목에 대해 "이 변경이 깨뜨릴 수 있는 테스트"를 미리 적어.
적을 수 없으면 그 항목은 안전망이 부족한 것이므로 표시해.

결과를 <계획 문서>에 저장하고 계획표를 보고해.

코드와 테스트를 수정하지 마. 이 단계는 계획만 세운다.
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<SHA>` | 2단계 안전망 커밋 |
| `<사용 가능한 도구>` | 실제로 쓸 수 있는 LSP·AST 도구. 없으면 기계적 갈래가 성립하지 않는다 |
| 나머지 | 앞 단계와 동일 |

## 주의

**갈래를 가르는 기준은 난이도가 아니라 정답의 존재 여부다.** 파일 200개에 걸친 이름 변경은 어렵지만 정답이 하나뿐이라 기계적이다. 함수 3줄을 어디로 옮길지는 쉬워 보여도 정답이 여럿이라 판단이다.

에이전트는 기계적 항목도 자기가 편집하려는 경향이 있다. **도구와 명령을 계획표에 명시적으로 적게 하는 것**이 그걸 막는다. 명령을 적을 수 없다면 그건 기계적 항목이 아니다.

판단 항목을 쪼개는 크기가 이 단계에서 가장 자주 틀린다. 기준은 하나다 — **테스트를 한 번 돌려서 성공·실패를 판정할 수 있는가.** 여러 변경이 얽혀 있으면 어느 것이 깨뜨렸는지 귀속되지 않는다.

`이 변경이 깨뜨릴 수 있는 테스트` 칸은 5단계에서 실제 결과와 대조하는 데 쓴다. 예상에 없던 테스트가 깨졌다면 변경이 계획한 범위를 넘었다는 신호다.
