- 계획표에 없는 항목 착수. 하는 김에 정리하고 싶은 것이 보여도
  손대지 말고 보고만 해

전부 끝나면 보고해:
- 항목별 결과 (적용 / 되돌림 + 원인)

### M3 되돌림 상세

```
FAIL test/integration/webhook.spec.ts > handles payment.captured
  TypeError: Cannot read properties of undefined (reading 'parse')
```

`ts-prune`이 미사용으로 보고한 `PaymentWebhookPayload`가 실제로는 쓰이고 있었다. 웹훅 핸들러가 문자열 키로 스키마를 조회한다.

```ts
const schema = schemaRegistry[`${event.type}Payload`]  // 정적 분석이 못 잡는다
```

`git checkout -- .`로 되돌렸다. 계획표에 표시:

> M3 — 도구로 처리 불가. 원인: 문자열 기반 동적 참조. 나머지 3개는 안전해 보이나 같은 패턴이 더 있을 수 있어 전체를 판단 갈래로 옮긴다. → **J0**으로 재분류, 사람 리뷰 필요

### 보고에 함께 올라온 것

> `OrderService.settle()` 안에 `#applyDiscount`와 `#recalcDiscount`가 거의 같은 일을 한다. 통합할 수 있어 보이지만 계획표에 없으므로 손대지 않았다.

계획표 J5로 추가하고 5단계에서 다룬다.

## 이 예제에서 볼 것

**M3에서 고치지 않고 되돌린 것**이 요점이다. 실제로 쓰이는 export 하나를 빼고 나머지 3개만 지우는 것도 가능했다. 하지만 그러면 `ts-prune`의 판정을 이미 한 번 틀린 채로 나머지를 신뢰하는 셈이다. 같은 문자열 기반 참조 패턴이 다른 곳에도 있을 수 있고, 그건 테스트가 없는 경로에서 조용히 깨진다.

되돌린 항목이 판단 갈래로 넘어가면서 **사람 리뷰가 붙는다.** 기계가 못 하는 일로 판명됐으니 사람이 봐야 한다는 것이 이 흐름의 논리다.

M1이 끝났으므로 이제 T1(`cancel()` 특성화 테스트 보강)을 할 수 있다. 테스트 동결의 유일한 예외이고, 계획표에 항목으로 올라와 있다.

에이전트가 **발견한 중복을 손대지 않고 보고만 한 것**도 규칙대로다. 계획표에 J5로 올린 뒤에 다룬다.
