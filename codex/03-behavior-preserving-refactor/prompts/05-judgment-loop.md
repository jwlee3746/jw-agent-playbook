# 5 · 판단 루프 — 템플릿

계획표의 판단 항목을 **한 건씩** 돈다. Worker가 바꾸고 Verifier가 판정한다.

## 프롬프트

```
[5 - 판단 루프 · 항목 <ID>]

기준선:
- 안전망 커밋: <SHA>
- 직전 정상 커밋: <SHA>          ← 되돌아갈 지점
- 테스트 경로: <테스트 경로> — 동결. 읽기만 한다
- 전체 테스트 명령: <테스트 명령>
- 기준 결과: <N passed>

역할:
- Worker(<하네스>): 항목 하나 적용. 테스트 실행과 통과 판정은 하지 않음
- Verifier(<하네스>): 동일 테스트 실행, 결과 보고. 코드 수정하지 않음

이번 항목: <ID> — <변경 내용>
대상 파일: <파일 목록>
예상되는 영향: <계획표의 "깨뜨릴 수 있는 테스트">

실행 순서:
1. Verifier: 변경 전 전체 테스트 실행. 기준 결과와 같은지 확인
2. Worker: 이 항목만 적용. 대상 파일 밖으로 나가지 않는다
3. Verifier: 동일 테스트 재실행
4. 판정:
   - 기준 결과와 동일 → 커밋하고 종료
   - 다름 → 깨진 테스트가 "예상되는 영향"에 있는지 확인
       있으면: 원인 하나에 최소 수정 (최대 2회)
       없으면: 변경이 계획 범위를 넘었다는 신호. 되돌린다
   - 재시도 2회를 넘기면 고치지 말고 되돌린다:
       git reset --hard <직전 정상 커밋>

금지:
- 테스트 파일 수정, 기대값 완화, skip·xfail 추가, 타임아웃 늘리기
- 동작 변경. 버그를 발견해도 고치지 말고 보고만 해
- 대상 파일 밖 수정
- 이번 항목 외의 변경. 한 번에 항목 하나
- 공개 인터페이스(export, 시그니처) 변경. 계획표에 명시된 것만

최종 보고:
- 적용 / 되돌림
- 테스트 결과 (기준 대비)
- 실제로 깨진 테스트와 예상의 차이
- 사람 리뷰가 필요한 판단이 있었으면 무엇인지
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<직전 정상 커밋>` | 매 항목마다 갱신된다. 되돌리기 지점 |
| `<기준 결과>` | 통과 수. 목록 비교는 6단계에서 하고 여기서는 수로 빠르게 판정한다 |
| `<파일 목록>` | 이 항목이 건드려도 되는 파일. 범위 이탈 판정 기준이 된다 |

## 주의

**항목 하나에 프롬프트 하나다.** 계획표를 통째로 주고 "순서대로 처리해"라고 하면 여러 항목이 한 커밋에 섞이고, 중간에 깨졌을 때 무엇이 원인인지 사라진다.

`예상되는 영향`과 실제를 대조하는 것이 이 단계의 판정 장치다. 예상에 없던 테스트가 깨졌다면 그건 변경이 계획한 것보다 넓게 퍼졌다는 뜻이고, **고칠 것이 아니라 되돌릴 신호**다.

### 되돌리기가 이른 이유

02는 재시도 상한까지 고친다. 여기서는 2회다. 리팩토링은 급하지 않고, **되돌리는 비용이 억지로 성사시키는 비용보다 항상 싸기 때문이다.** 억지로 통과시킨 리팩토링은 구조가 나아지지도 않은 채 diff만 남긴다.

되돌린 항목은 **더 작게 쪼개서 계획표에 다시 넣는다.** 같은 크기로 다시 던지면 같은 결과가 나온다.

### 테스트 동결을 권한으로 막기

프롬프트의 금지보다 확실한 방법이 있으면 그걸 쓴다.

- 하네스에 경로별 쓰기 제한이 있으면 `<테스트 경로>`를 읽기 전용으로 설정
- 없으면 pre-commit 훅에서 테스트 경로 diff를 거부
- 계획표에 예외 항목(T1 같은)이 있을 때만 잠시 연다

## 사람 리뷰

`사람 리뷰: 예`인 항목은 커밋 후 **다음 항목으로 넘어가기 전에** 사람이 본다. 테스트는 동작이 같다는 것만 말해주므로, 추상화가 도메인에서 말이 되는지는 여기서만 걸러진다.
