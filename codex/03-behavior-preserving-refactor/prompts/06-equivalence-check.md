# 6 · 동등성 검증 — 템플릿

전체 테스트 통과는 필요조건일 뿐이다. **기준선이 움직이지 않았는지**를 따로 확인한다.

## 프롬프트

```
[6 - 동등성 검증]

기준선:
- 안전망 커밋: <SHA>
- 테스트 경로: <테스트 경로>
- 전체 테스트 명령: <테스트 명령>
- 안전망 커밋 시점 결과: <N passed>

Verifier가 단독으로 수행한다. 이 단계에서 코드와 테스트를 수정하지 않는다.

1. 테스트 동결 확인
   git diff <SHA> HEAD -- <테스트 경로>
   비어 있어야 한다. 비어 있지 않으면 각 변경을 계획표의 예외 항목과
   대조해. 계획표에 없는 테스트 변경은 전부 보고한다.

2. 결과 동등성 확인
   현재 전체 테스트를 실행하고, 통과 수가 아니라 테스트 이름 목록을
   안전망 커밋 시점 목록과 비교해.
   사라진 테스트, 이름이 바뀐 테스트를 찾아 보고한다.

3. 구조 변경 확인
   계획표의 각 항목에 대해, 의도한 구조 변경이 실제로 일어났는지
   기계로 확인해. 보고서를 믿지 말고 코드에서 센다:
   <구조 확인 방법>

4. 공개 인터페이스 확인
   git diff <SHA> HEAD 에서 export 목록과 공개 시그니처 변경을
   추출해. 계획표에 명시되지 않은 변경은 전부 보고한다.

5. 범위 확인
   git diff --stat <SHA> HEAD
   계획표의 대상 파일 목록에 없는 파일이 변경됐으면 보고한다.

보고 형식:
| 확인 | 결과 | 문제 |
5개 항목 각각에 대해 통과/실패와 근거를 적는다.

하나라도 실패면 무엇을 되돌려야 하는지 제안하되,
되돌리기를 실행하지는 마.
```

### 구조 확인 방법 예

| 언어 | 도구 | 세는 것 |
|---|---|---|
| TypeScript | `ts-morph` 스크립트 | 클래스별 메서드 수, 심볼이 있는 파일, 파일별 라인 |
| Python | `ast` 모듈 | 함수가 최상위인지, 클래스 노드 수 |
| Java | `javaparser` | 클래스별 메서드 수, 패키지 위치 |
| 언어 무관 | `git diff --stat` + LSP `workspace/symbol` | 심볼 위치 이동 |

[Aider의 리팩토링 벤치마크](https://github.com/Aider-AI/refactor-benchmark)가 쓰는 판정이 이 형태다. 함수가 실제로 최상위로 나왔는지, 원래 클래스가 실제로 줄었는지를 AST로 센다.

## 주의

**Verifier 단독으로 돌린다.** 변경을 만든 주체가 동등성을 판정하면 자기가 의도한 것을 확인하게 된다. 3번(구조 변경 확인)이 특히 그렇다 — Worker에게 물으면 "추출했습니다"라고 답하고, 실제로는 메서드가 그대로 있고 래퍼만 생긴 경우가 있다.

1번이 이 설계에서 가장 중요한 확인이다. 테스트가 바뀌지 않았다는 것이 확인돼야 나머지 통과가 의미를 갖는다. **순서를 1번으로 둔 이유가 그것이다.**

2번에서 통과 수가 아니라 이름 목록을 비교하는 이유: 테스트 3개가 사라지고 3개가 생기면 수는 같다.

5번은 4단계에서 금지한 "하는 김에" 변경을 사후에 잡는다. 프롬프트 금지를 빠져나간 것이 여기서 diff로 드러난다.

## 이 단계가 답하지 못하는 것

여섯 단계를 다 통과해도 남는 질문이 있다.

- 새 추상화가 이 도메인에서 말이 되는가
- 바꾼 이름이 팀 용어와 맞는가
- 쪼갠 단위가 앞으로 같이 변경될 것들끼리 묶여 있는가

**동등성 검증은 동작이 같다는 것만 말해준다. 구조가 나아졌는지는 말해주지 않는다.** 계획표의 `사람 리뷰` 칸이 이 질문들의 자리이고, 이 단계 뒤에 사람이 한 번 더 본다.
