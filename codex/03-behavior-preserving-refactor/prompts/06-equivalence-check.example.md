# 6 · 동등성 검증 — 예제

J5까지 전부 적용한 뒤 돌린다.

## 프롬프트

```
[6 - 동등성 검증]

기준선:
- 안전망 커밋: a3f81c2
- 테스트 경로: test/
- 전체 테스트 명령: npx vitest run
- 안전망 커밋 시점 결과: 58 passed

Verifier가 단독으로 수행한다. 이 단계에서 코드와 테스트를 수정하지 않는다.

1. 테스트 동결 확인
   git diff a3f81c2 HEAD -- test/
   비어 있어야 한다. 비어 있지 않으면 각 변경을 계획표의 예외 항목과
   대조해. 계획표에 없는 테스트 변경은 전부 보고한다.
   (계획표의 유일한 예외: T1 — cancel() 특성화 테스트 3건 추가)

2. 결과 동등성 확인
   npx vitest run --reporter=json 으로 테스트 이름 목록을 뽑고,
   안전망 커밋 시점 목록과 비교해.
   사라진 테스트, 이름이 바뀐 테스트를 찾아 보고한다.

3. 구조 변경 확인
   계획표의 각 항목에 대해, 의도한 구조 변경이 실제로 일어났는지
   기계로 확인해. 보고서를 믿지 말고 코드에서 센다.
   ts-morph 스크립트로:
   - OrderService의 메서드 수와 라인 수
   - NotificationService, InventoryCoordinator, RetryPolicy가
     실제로 존재하고 각자 의도한 메서드를 갖는지
   - mailer/sms 참조가 OrderService에서 사라졌는지

4. 공개 인터페이스 확인
   git diff a3f81c2 HEAD 에서 export 목록과 공개 시그니처 변경을
   추출해. 계획표에 명시되지 않은 변경은 전부 보고한다.

5. 범위 확인
   git diff --stat a3f81c2 HEAD
   계획표의 대상 파일 목록에 없는 파일이 변경됐으면 보고한다.

보고 형식:
| 확인 | 결과 | 문제 |
5개 항목 각각에 대해 통과/실패와 근거를 적는다.

하나라도 실패면 무엇을 되돌려야 하는지 제안하되,
되돌리기를 실행하지는 마.
```

## 나온 보고

| 확인 | 결과 | 문제 |
|---|---|---|
| 1 테스트 동결 | **경고** | T1 3건 추가는 계획표 예외로 확인됨. 그 외 `settle.spec.ts`에서 1줄 변경 발견 |
| 2 결과 동등성 | 통과 | 58 → 61. 사라지거나 이름 바뀐 테스트 없음 |
| 3 구조 변경 | 통과 | 아래 표 참조 |
| 4 공개 인터페이스 | 통과 | `OrderService`의 export·시그니처 동일. 신규 3개는 계획표에 있음 |
| 5 범위 | **경고** | `src/order/utils.ts`가 변경됨. 계획표 대상 파일에 없음 |

### 1번 상세

```diff
 test/characterization/settle.spec.ts
-    }, 5000)
+    }, 15000)
```

타임아웃이 5초에서 15초로 늘어났다. **계획표에 없는 테스트 변경이다.** J3에서 `RetryPolicy`가 재시도 간 대기를 넣으면서 테스트가 느려졌고, 그 과정에서 늘린 것으로 보인다.

이건 5단계 금지 항목(`타임아웃 늘리기`)에 정확히 걸린다. 그리고 더 중요한 건 **대기 시간이 늘었다는 것 자체가 동작 변경**이라는 점이다. 원래 재시도는 즉시 재시도였다.

> 제안: J3을 되돌리고, 대기 없는 재시도로 다시 적용한 뒤 타임아웃 변경을 revert한다.

### 3번 상세

```
OrderService:  메서드 14 → 6,  라인 620 → 218
NotificationService:  존재, 메서드 3 (notifyCustomer, sendSms, sendMail)
InventoryCoordinator: 존재, 메서드 4
RetryPolicy:          존재, 메서드 2
OrderService 내 mailer/sms 참조: 0건
```

계획한 구조 변경이 실제로 일어났다. 래퍼만 만들고 원래 메서드를 남겨두는 경우가 아니다.

### 5번 상세

```
 src/order/utils.ts | 12 +++++-----
```

`formatOrderId()`의 구현이 바뀌었다. 계획표 어느 항목에도 없다. J1 커밋에 섞여 들어갔다.

> 제안: 이 파일의 변경만 따로 revert한다. 개선이 필요하면 별도 항목으로 올린다.

## 이 예제에서 볼 것

**61 passed로 전부 통과했는데 두 가지 문제가 나왔다.** 테스트만 봤으면 완료로 처리됐을 것이다.

타임아웃 변경이 가장 위험한 종류다. 테스트를 고쳐서 통과시킨 것이고, 그 뒤에 **재시도 대기라는 동작 변경**이 숨어 있다. 1번 확인이 없었으면 "리팩토링만 했는데 결제 응답이 느려졌다"로 나중에 드러난다.

`utils.ts`는 4단계에서 금지한 "하는 김에" 변경이다. 프롬프트 금지를 빠져나갔고, 5번 diff 확인이 잡았다. **금지를 프롬프트에만 걸어두면 이렇게 새므로 사후 확인이 필요하다.**

3번이 통과한 것도 그냥 넘길 게 아니다. 메서드 14 → 6, 라인 620 → 218은 기계가 센 숫자다. 에이전트가 "추출을 완료했습니다"라고 보고한 것과는 다른 종류의 근거다.
