# 4 · 기계적 일괄 적용 — 템플릿

계획표의 기계적 항목을 **도구로** 처리한다. 에이전트는 도구를 돌리고 결과를 확인하는 역할만 한다.

## 프롬프트

```
[4 - 기계적 일괄 적용]

기준선:
- 안전망 커밋: <SHA>
- 테스트 경로: <테스트 경로> — 동결. 읽기만 한다
- 전체 테스트 명령: <테스트 명령>

계획 문서 <계획 문서>의 계획표에서 갈래가 [기계적]인 항목을
의존성 순서대로 처리해.

각 항목마다:
1. 계획표에 적힌 도구 명령을 실행한다
2. 전체 테스트를 실행한다
3. 판정:
   - 전과 동일하게 통과 → 커밋한다. 커밋 메시지에 항목 ID를 넣는다
   - 하나라도 다르면 → 고치지 말고 즉시 되돌린다:
       git checkout -- .
     그리고 그 항목을 "도구로 처리 불가"로 표시하고 원인을 적는다.
     원인 후보: 리플렉션, 문자열 기반 참조, 동적 import,
     타입 단언으로 가려진 참조
4. 다음 항목으로 간다

절대 하지 말 것:
- 도구 대신 파일을 직접 편집하는 것. 이름 변경과 이동은
  반드시 LSP/AST 도구로 한다. 텍스트 치환은 참조를 놓친다
- 테스트가 깨졌을 때 코드를 고쳐서 통과시키는 것. 되돌린다
- 테스트 파일 수정
- 계획표에 없는 항목 착수. 하는 김에 정리하고 싶은 것이 보여도
  손대지 말고 보고만 해

전부 끝나면 보고해:
- 항목별 결과 (적용 / 되돌림 + 원인)
- 되돌린 항목 목록 — 이것들은 5단계 판단 갈래로 옮긴다
- 현재 테스트 결과가 안전망 커밋과 동일한지
```

## 채울 것

앞 단계와 동일하다. `<SHA>`와 `<테스트 경로>`를 매번 다시 적는 것이 이 설계의 규칙이다.

## 주의

**고치지 않고 되돌린다**가 이 단계의 규칙이고, [02](../../02-aorr-worker-verifier-loop/)와 정반대인 지점이다. 02는 실패하면 원인 하나를 최소 수정한다. 여기서는 되돌린다.

이유: 기계적 변경이 테스트를 깨뜨렸다는 것은 **그 변경이 기계적이지 않았다는 증거**다. 도구가 놓친 참조가 있다는 뜻이고, 놓친 참조는 대개 테스트가 없는 곳에도 있다. 손으로 메우면 보이는 것만 메우게 된다. 판단 갈래로 옮겨서 사람 리뷰를 붙이는 것이 맞다.

"하는 김에 정리하고 싶은 것"에 대한 금지가 실전에서 가장 자주 깨진다. 에이전트는 이름을 바꾸다가 옆의 중복도 정리하고 싶어 한다. 그렇게 들어간 변경은 계획표에 없어서 6단계 대조에서 정체불명의 diff로 나타난다.

## 커밋 단위

**항목 하나 = 커밋 하나.** 되돌리기 단위가 커밋이라서 그렇다. 여러 항목을 한 커밋에 묶으면 하나가 잘못됐을 때 나머지도 같이 날아간다.
