# 03 · 동작 보존 리팩토링

**한 줄**: 겉보기 동작을 고정해두고 구조만 바꾼다. 기계가 할 수 있는 변경은 기계에 맡기고, 에이전트에게는 판단이 필요한 것만 한 건씩 준다.
**출처**: 자작 — 외부 자료를 종합했다. 근거는 [참고](#참고)에 링크와 발췌로 둔다
**상태**: 미검증
**포팅**: [claude/03](../../claude/03-behavior-preserving-refactor/)

## 용도

기능을 더하지 않고 **구조만 바꾸는 작업**에 쓴다. 중복 제거, 거대 함수·클래스 분해, 계층 정리, 죽은 코드 제거, 인터페이스 통일.

쓰면 안 되는 경우가 셋 있다.

| 상황 | 왜 |
|---|---|
| **테스트가 없다** | 동작 보존을 확인할 방법이 없다. 이 설계 전체가 "전후 동작이 같다"는 판정에 걸려 있다. 안전망을 먼저 만드는 것이 1·2단계이지만, 그것조차 불가능한 코드면 이 설계를 쓸 수 없다 |
| **동작도 같이 바꾼다** | 리팩토링과 기능 변경을 한 커밋에 섞으면 테스트가 깨졌을 때 어느 쪽 탓인지 알 수 없다. 기능 변경은 [02](../02-aorr-worker-verifier-loop/)로 따로 돌린다 |
| **이름 변경·파일 이동만 필요하다** | 에이전트를 부를 일이 아니다. LSP의 rename symbol이나 AST 도구가 정확하고 빠르다. 4단계가 이걸 다룬다 |

## 전제

- 하네스 / 모델: Codex CLI 또는 동급의 파일 수정 에이전트. 검증은 별도 주체 (02와 같은 이유)
- 필요한 툴·권한: 테스트 러너, 커버리지 측정, 언어별 LSP 또는 AST 변환 도구, git
- 레포·환경 조건: **되돌릴 수 있어야 한다.** 각 단계가 독립 커밋이 되고, 언제든 직전 커밋으로 돌아갈 수 있는 상태

## [02](../02-aorr-worker-verifier-loop/)와 무엇이 다른가

같은 Worker/Verifier 분리를 쓴다. 다른 것은 **통과의 정의**다.

| | 02 (기능 구현) | 03 (리팩토링) |
|---|---|---|
| 통과 기준 | 테스트가 통과한다 | **전후 테스트 결과가 같고, 테스트 파일이 안 바뀌었다** |
| 실패했을 때 | 코드를 고친다 | 코드를 고치거나 **되돌린다** |
| 테스트 | 루프의 산출물 | 루프의 **전제**. 건드리면 안 되는 기준선 |

이 차이가 프롬프트 전반을 지배한다. 02는 "테스트를 통과시켜라"이고, 03은 "**테스트를 건드리지 말고** 통과시켜라"다. 리팩토링에서 에이전트가 가장 흔히 하는 부정행위가 테스트를 기대값에 맞춰 고치는 것이라, 이 금지가 여러 단계에 반복해서 들어간다.

# 전체 절차

여섯 단계, 세 국면이다. **안전망이 서기 전에는 프로덕션 코드를 건드리지 않는다.**

| 국면 | 단계 | 프로덕션 코드 | 테스트 코드 |
|---|---|---|---|
| **A. 안전망** | 1 범위와 진단 → 2 특성화 테스트 | 건드리지 않음 | 추가만 |
| **B. 변경** | 3 분류와 계획 → 4 기계적 일괄 → 5 판단 루프 | 3은 계획만, 4·5는 수정 | **동결** |
| **C. 확인** | 6 동등성 검증 | 건드리지 않음 | 건드리지 않음 |

# 국면 A · 안전망

## 1. 범위와 진단

**무엇을 리팩토링할지 정하기 전에, 무엇이 지금 검증되고 있는지부터 센다.**

세 가지를 만든다.

1. **대상 목록** — 파일과 심볼 단위. "결제 모듈"이 아니라 `PaymentProcessor.settle()`
2. **안전망 지도** — 대상별로 현재 테스트가 어디까지 덮는지. 라인 커버리지가 아니라 **분기와 예외 경로**를 본다
3. **공백 목록** — 덮이지 않은 경로. 이게 2단계의 입력이 된다

여기서 리팩토링을 시작하지 않는다. 진단만 한다.

### 추정하지 않는다

커버리지는 **측정한 숫자**를 쓴다. 에이전트에게 "이 코드는 테스트가 잘 되어 있나"를 물으면 코드를 읽고 그럴듯한 답을 낸다. 커버리지 도구를 돌린 출력이 아니면 안전망 지도에 넣지 않는다.

## 2. 특성화 테스트

**지금 코드가 실제로 하는 일을 그대로 고정하는 테스트**를 쓴다. 옳은 동작이 아니라 현재 동작이다.

이름이 특성화(characterization)인 이유가 여기 있다. 기존 동작이 버그여도 **그 버그를 그대로 기록한다.** 리팩토링 중에 버그를 고치면 테스트가 깨지고, 그러면 구조를 잘못 바꾼 것인지 버그를 고쳐서인지 구분할 수 없다.

```
발견한 버그 → 고치지 않는다 → 현재 동작으로 테스트에 기록 → 별도 이슈로 남긴다
```

### 무엇을 고정하나

| 종류 | 예 |
|---|---|
| 반환값 | 정상 입력, 경계값, 빈 입력 |
| 예외 | 어떤 입력에 어떤 예외가 어떤 메시지로 |
| 부수효과 | 호출되는 외부 함수, 쓰이는 파일, 발행되는 이벤트, 그 **순서** |
| 상태 변화 | 호출 전후의 객체 상태 |

부수효과와 순서가 자주 빠진다. 반환값만 고정하면 에이전트가 내부를 재배치하면서 호출 순서를 바꿔도 테스트가 통과한다.

### 안전망 판정

2단계가 끝나면 **1단계의 공백 목록이 비어야 한다.** 비지 않으면 그 대상은 리팩토링 범위에서 뺀다. 덮이지 않은 경로를 리팩토링하는 것은 검증 없이 고치는 것과 같다.

이 시점에서 **커밋한다.** 안전망만 들어간 커밋이 되돌아갈 기준점이 된다.

# 국면 B · 변경

## 3. 분류와 계획

여기가 이 설계의 핵심이다. **모든 변경을 두 갈래로 가른다.**

| 갈래 | 무엇 | 누가 | 검증 |
|---|---|---|---|
| **기계적** | 이름 변경, 파일·심볼 이동, 시그니처 순서, 문법 현대화, import 정리 | LSP / AST 도구 | 도구가 보장 + 테스트 |
| **판단** | 함수 분해, 책임 재배치, 중복 통합, 추상화 도입, 조건문 구조 변경 | 에이전트 한 건씩 | 테스트 + 사람 리뷰 |

**기계적인 것을 에이전트에게 주지 않는다.** 이름 변경을 텍스트 치환으로 하면 참조를 놓치고, 놓친 참조는 테스트가 없는 경로에서 조용히 깨진다. LSP의 rename symbol은 이걸 구조적으로 처리한다.

반대로 판단이 필요한 것을 도구로 하려 하지 않는다. "이 함수를 어디로 옮겨야 하는가"에 정답 도구는 없다.

### 계획표

```
ID | 대상 | 갈래 | 변경 내용 | 의존성 | 되돌리기 단위 | 위험도 | 사람 리뷰
```

**의존성 순서가 실행 순서**가 된다. 그리고 순서에는 규칙이 하나 있다.

> 기계적 변경을 먼저, 판단 변경을 나중에.

이름과 위치가 정리된 뒤에 구조를 보면 무엇이 진짜 중복인지 드러난다. 반대로 하면 구조를 바꾼 뒤 이름을 정리하다가 방금 만든 추상화를 다시 건드리게 된다.

### 범위 기대치

실증 연구를 보면 에이전트가 실제로 해내는 리팩토링은 변수 타입 변경, 파라미터 이름 변경 같은 **국소 작업에 몰려 있다**([참고](#참고)). 아키텍처 개조를 한 건으로 던지면 안 된다. 3단계에서 사람이 국소 단위로 쪼개는 것이 이 설계가 요구하는 일이다.

## 4. 기계적 일괄 적용

도구로 처리하고, 에이전트는 **도구를 고르고 돌리고 결과를 보고하는 역할**만 한다.

```
1. 변경 하나당 도구 명령 하나
2. 실행
3. 전체 테스트 — 하나라도 깨지면 즉시 되돌린다
4. 커밋 (변경 하나 = 커밋 하나)
```

3번에서 **고치지 않고 되돌리는 것**이 02와 다른 점이다. 기계적 변경이 테스트를 깨뜨렸다면 도구가 처리 못 하는 경우(리플렉션, 문자열 참조, 동적 import)라는 뜻이고, 그건 손으로 고칠 게 아니라 판단 갈래로 옮겨야 할 항목이다.

## 5. 판단 루프

계획표의 판단 항목을 **한 건씩** 돈다. 사이클은 02와 같되 금지 항목이 다르다.

```
변경 전 전체 테스트 (green 확인)
  → Worker가 항목 하나 적용
  → Verifier가 동일 테스트 재실행
  → 결과가 전과 다르면: 원인 하나 최소 수정 또는 되돌리기
  → green이면 커밋하고 다음 항목
```

### 금지

| 금지 | 막는 것 |
|---|---|
| **테스트 파일 수정** | 기준선을 움직여서 통과시키는 것 |
| **기대값 완화, `skip`·`xfail` 추가** | 위와 같음 |
| 동작 변경 — 버그 수정 포함 | 리팩토링과 기능 변경이 섞이는 것 |
| 계획표에 없는 항목 착수 | 범위가 조용히 넓어지는 것 |
| 한 번에 두 항목 이상 | 무엇이 깨뜨렸는지 귀속되지 않는 것 |

첫 두 개가 이 설계에서 가장 중요하다. **테스트 파일을 읽기 전용으로 만들 수 있으면 그렇게 한다.** 프롬프트로 금지하는 것보다 권한으로 막는 편이 확실하다.

### 되돌리기 기준

02는 재시도 상한까지 고친다. 03은 **더 일찍 되돌린다.**

- 한 항목에 재시도 2회를 넘기면 되돌린다
- 수정 범위가 계획한 파일 밖으로 나가면 되돌린다
- 리팩토링은 급하지 않다. 되돌리는 비용이 억지로 성사시키는 비용보다 항상 싸다

# 국면 C · 확인

## 6. 동등성 검증

전체 테스트 통과는 필요조건이지 충분조건이 아니다. 네 가지를 따로 확인한다.

| 확인 | 방법 | 무엇을 잡나 |
|---|---|---|
| **테스트가 안 바뀌었다** | `git diff <안전망 커밋> -- <테스트 경로>`가 비어 있음 | 기준선을 움직인 통과 |
| **전후 결과가 같다** | 안전망 커밋의 테스트 결과와 지금 결과를 비교 (통과 수뿐 아니라 목록) | 조용히 사라진 테스트 |
| **구조가 실제로 바뀌었다** | 계획표 항목별로 심볼이 의도한 위치에 있는지 기계로 확인 | "리팩토링했다"고 보고만 한 경우 |
| **공개 인터페이스가 그대로다** | export 목록, 시그니처, 공개 API 스냅샷 비교 | 내부 정리 중에 새어나간 외부 변경 |

세 번째는 [Aider의 리팩토링 벤치마크](https://github.com/Aider-AI/refactor-benchmark)가 쓰는 방식이다. 함수가 실제로 최상위로 나왔는지, 원래 클래스가 실제로 줄었는지를 AST로 센다. 모델의 자기 보고가 아니라 기계가 세는 값이라 신뢰할 수 있다.

## 사람이 봐야 하는 것

여섯 단계를 다 통과해도 기계가 답하지 못하는 질문이 남는다.

- 새로 만든 추상화가 **이 도메인에서 말이 되는가**
- 바꾼 이름이 팀이 쓰는 용어와 맞는가
- 쪼갠 단위가 앞으로 같이 변경될 것들끼리 묶여 있는가

테스트는 동작이 같다는 것만 말해준다. **구조가 나아졌는지는 말해주지 않는다.** 리팩토링을 끝까지 자동화하지 못하는 이유가 여기 있고, 5단계 계획표에 `사람 리뷰` 칸을 둔 이유도 같다.

---

## 이 설계의 요점

1. **안전망이 먼저다.** 테스트 없이 리팩토링하면 그냥 코드를 바꾸는 것이다.
2. **특성화 테스트는 옳은 동작이 아니라 현재 동작을 고정한다.** 버그도 그대로 기록한다.
3. **기계적 변경과 판단 변경을 가른다.** 정확도와 비용이 둘 다 여기서 갈린다.
4. **테스트 파일을 동결한다.** 프롬프트로 금지하고, 가능하면 권한으로 막는다.
5. **일찍 되돌린다.** 리팩토링은 급하지 않다.
6. **통과했다고 나아진 것은 아니다.** 구조 판단은 사람 몫으로 남는다.

3번은 [02](../02-aorr-worker-verifier-loop/)의 "기계가 판정하고 모델은 판단에만"과 같은 원리다. 02는 **검증**에 적용했고, 여기서는 **변경 자체**에 적용한다.
