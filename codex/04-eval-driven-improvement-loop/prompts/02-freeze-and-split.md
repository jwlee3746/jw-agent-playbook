# 2 · 분할과 동결 — 템플릿

dev와 holdout을 나누고, 골든셋을 동결하고, 기준선 점수를 기록한다. 최초 1회만 돈다.

## 프롬프트

```
[2 - 분할과 동결]

실패 분류표: <분류표 파일>
골든셋 경로: <골든셋 경로>
평가 명령: <평가 명령>

1. 분할
   골든셋을 dev와 holdout으로 나눠. 비율 <비율>.
   무작위로 나누지 마. 분류표의 각 실패 유형이 양쪽에
   비슷한 비율로 들어가게 층화(stratified) 분할해.
   유형별로 몇 건씩 갔는지 표로 보고해.
   한쪽에 3건 미만이 되는 유형이 있으면 그 사실을 표시해 —
   그 유형은 게이트에서 통계적으로 판정할 수 없다.

2. 분할 결과를 파일로 고정해
   케이스 ID 목록을 <dev 목록 파일>, <holdout 목록 파일>에 저장해.
   매 실행마다 다시 나누면 회차 간 점수 비교가 깨진다.

3. 동결 선언
   다음을 동결 대상으로 <루프 기록>에 명시해:
   - 골든셋 케이스 파일
   - 기대값·라벨
   - judge rubric과 채점 코드
   - holdout 목록 파일
   동결 예외는 없다. 데이터 수정은 D 트랙 별도 절차로만 한다.

4. 기준선 측정
   dev와 holdout 각각에 대해 평가를 실행하고 기록해:
   회차 0 | 커밋 SHA | dev 점수 | holdout 점수 |
   유형별 실패 수 | 평가 설정(모델·온도·시드)

   평가 설정을 반드시 남겨. 모델 버전이 바뀌면 점수가 움직이고,
   그 움직임을 개선으로 읽으면 안 된다.

5. 재현성 확인
   dev 평가를 2회 실행해서 점수가 같은지 확인해.
   다르면 그 편차를 기록해. 편차보다 작은 개선은
   게이트에서 통과로 판정하면 안 된다.

결과를 <루프 기록>에 저장해.

시스템(프롬프트·예제·코드)을 수정하지 마. 이 단계는 기준선만 만든다.
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<비율>` | dev 60~70% / holdout 30~40% |
| `<dev 목록 파일>` / `<holdout 목록 파일>` | 케이스 ID 목록. 이것도 동결 대상 |
| `<루프 기록>` | 회차별 기록이 쌓일 파일. [02의 MEMORY](../../02-aorr-worker-verifier-loop/MEMORY-template.md)와 같은 역할 |

## 주의

**5번이 자주 빠지고, 빠지면 루프 전체가 노이즈를 쫓는다.** LLM 평가는 온도·샘플링·judge 편차 때문에 같은 시스템에 다른 점수를 낸다. 그 편차가 2점인데 게이트가 1점 개선을 통과시키면, 루프는 아무것도 안 고치고 점수만 흔들며 돈다.

측정한 편차를 게이트의 최소 개선폭으로 쓴다.

### rubric을 동결 대상에 넣는 이유

rubric은 **기준이지 시스템이 아니다.** "톤이 자연스러울 것"을 "톤이 부적절하지 않을 것"으로 고치면 점수가 오른다. 그건 개선이 아니라 채점 완화다.

에이전트에게 rubric을 열어주면 이 경로를 반드시 찾는다. 점수를 올리는 가장 싼 방법이기 때문이다.

### 3건 미만 유형

층화 분할을 해도 희귀 유형은 한쪽에 3건 미만으로 떨어진다. 그런 유형은 **게이트에서 판정하지 않는다** — 1건이 오가는 것을 개선·퇴행으로 읽으면 안 된다. 대신 6단계 감사에서 누적으로 본다.

## 권한으로 막기

프롬프트 금지보다 확실한 것이 있으면 그걸 쓴다.

- 하네스에 경로별 쓰기 제한이 있으면 골든셋 경로를 읽기 전용으로
- 없으면 pre-commit 훅에서 골든셋 경로 diff를 거부
- D 트랙이 승인됐을 때만 잠시 열고, 연 사실을 루프 기록에 남긴다
