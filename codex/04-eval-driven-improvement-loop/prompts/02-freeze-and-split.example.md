# 2 · 분할과 동결 — 예제

1단계에서 rubric을 고치고 A1 케이스를 추가한 뒤, 전체 재평가를 마친 상태에서 시작한다. 케이스는 200건 → 216건이 됐다.

## 프롬프트

```
[2 - 분할과 동결]

실패 분류표: docs/failure-taxonomy.md
골든셋 경로: eval/golden/
평가 명령: python -m eval.run --set <set> --seed 42

1. 분할
   골든셋 216건을 dev와 holdout으로 나눠. 비율 65:35.
   무작위로 나누지 마. 분류표의 각 실패 유형(T1~T6, A1)이 양쪽에
   비슷한 비율로 들어가게 층화 분할해.
   유형별로 몇 건씩 갔는지 표로 보고해.
   한쪽에 3건 미만이 되는 유형이 있으면 그 사실을 표시해 —
   그 유형은 게이트에서 통계적으로 판정할 수 없다.

2. 분할 결과를 파일로 고정해
   케이스 ID 목록을 eval/splits/dev.txt, eval/splits/holdout.txt에 저장해.
   매 실행마다 다시 나누면 회차 간 점수 비교가 깨진다.

3. 동결 선언
   다음을 동결 대상으로 docs/loop-log.md에 명시해:
   - eval/golden/ 전체
   - eval/judge_rubric.md
   - eval/scoring.py
   - eval/splits/holdout.txt
   동결 예외는 없다. 데이터 수정은 D 트랙 별도 절차로만 한다.

4. 기준선 측정
   dev와 holdout 각각에 대해 평가를 실행하고 기록해:
   회차 0 | 커밋 SHA | dev 점수 | holdout 점수 |
   유형별 실패 수 | 평가 설정(모델·온도·시드)

5. 재현성 확인
   dev 평가를 2회 실행해서 점수가 같은지 확인해.
   다르면 그 편차를 기록해. 편차보다 작은 개선은
   게이트에서 통과로 판정하면 안 된다.

결과를 docs/loop-log.md에 저장해.

시스템(프롬프트·예제·코드)을 수정하지 마. 이 단계는 기준선만 만든다.
```

## 나온 결과

### 분할

| 유형 | 전체 | dev | holdout | 비고 |
|---|---|---|---|---|
| T1 | 18 | 12 | 6 | |
| T2 | 11 | 7 | 4 | |
| T3 | 9 | 6 | 3 | |
| T4 | 12 | 8 | 4 | |
| T5 | 7 | 5 | 2 | **holdout 3건 미만** |
| T6 | 5 | 3 | 2 | **holdout 3건 미만** |
| A1 | 4 | 3 | 1 | **holdout 3건 미만** |
| 정상 | 150 | 96 | 54 | |
| **계** | **216** | **140** | **76** | |

T5·T6·A1은 holdout이 3건 미만이다. **게이트에서 이 유형들의 개선·퇴행은 판정하지 않는다.** 6단계 감사에서 누적으로 본다.

### 기준선

```
회차 0 | 커밋 7b3e19f
dev      82.1점 (140건 중 실패 25건)
holdout  80.4점 (76건 중 실패 15건)

유형별 실패 (dev): T1 12, T4 8, T2 7, T3 6, T5 5, T6 3, A1 3
평가 설정: judge=claude-sonnet-4-5 / temp=0.0 / seed=42 / eval commit 7b3e19f
```

### 재현성

```
1회차: dev 82.1
2회차: dev 81.4
편차: 0.7점
```

온도를 0으로 고정했는데도 0.7점이 흔들린다. 툴 응답 지연에 따른 타임아웃 경계 케이스 2건이 실행마다 갈렸다.

> **게이트 최소 개선폭을 1.5점(편차의 2배)으로 정한다.** 이보다 작은 개선은 통과로 판정하지 않는다.

### 동결 선언 (`docs/loop-log.md`)

```
동결 대상 (읽기만 가능):
  eval/golden/**
  eval/judge_rubric.md
  eval/scoring.py
  eval/splits/holdout.txt

holdout 개봉 기록:
  회차 0 — 기준선 측정 (1회)
```

## 이 예제에서 볼 것

**0.7점 편차를 측정한 것**이 이 단계에서 가장 값어치 있는 산출물이다. 이걸 재지 않았다면 게이트가 "82.1 → 82.6, 개선"으로 판정했을 것이고, 루프는 아무것도 안 고치면서 회차를 쌓았을 것이다.

편차의 원인(타임아웃 경계 케이스)이 밝혀진 것도 소득이다. 이건 **C 트랙 항목**이다 — 평가 자체를 안정시키는 것이 어떤 개선보다 먼저다.

**holdout 3건 미만 유형을 미리 표시한 것**은 나중에 나올 오독을 막는다. T5가 holdout에서 2건 중 1건 개선되면 "50% 개선"으로 보이지만 통계적으로 아무 의미가 없다.

**`holdout 개봉 기록`을 처음부터 만든 것**에 주목할 것. 6단계에서 이 숫자가 회차 수에 가까워지면 holdout이 사실상 dev가 됐다는 신호다.
