# 4 · 개입 실행 — 템플릿

3단계가 정한 변경 하나를 적용한다. 트랙별로 규칙이 다르다.

## 프롬프트 — 공통

```
[4 - 개입 실행 · 회차 <N> · 트랙 <X>]

기준선:
- 직전 통과 회차: <N-1> / 커밋 <SHA>      ← 되돌아갈 지점
- 골든셋 경로: <골든셋 경로> — 동결. 읽기만 한다
- 평가 명령(dev): <dev 명령>
- 평가 명령(holdout): <holdout 명령> — 5단계에서만 실행
- 현재 점수: dev <값>

이번 회차 계획: <루프 기록>의 회차 <N> 항목
대상 유형: <유형>
지문: <지문>
변경 내용: <무엇을 바꾸나>
허용 파일: <이 회차가 건드려도 되는 파일 목록>

실행 순서:
1. 계획된 변경 하나만 적용한다
2. dev 평가를 실행한다
3. 결과를 유형별로 집계해서 보고한다 (총점만 보고하지 마)
4. 멈춘다. 게이트 판정은 5단계에서 다른 주체가 한다

금지:
- 골든셋·기대값·rubric·채점 코드 수정
- holdout 평가 실행, holdout 케이스 열람
- 허용 파일 밖 수정
- 계획에 없는 추가 변경. 하는 김에 고치고 싶은 것이 보여도
  손대지 말고 보고만 해
- 점수가 안 오른다고 다른 변경을 시도하는 것.
  1회 적용하고 멈춘다

기대값이 틀렸다고 판단되면 고치지 말고 D 트랙 제안으로 보고해:
  케이스 ID | 현재 기대값 | 왜 틀렸다고 보나 | 근거(스펙·도메인 규칙)
이번 회차 트랙이 D이면 아무것도 적용하지 말고
상태를 DATA_APPROVAL_REQUIRED로 두고 멈춰.

최종 보고:
- 무엇을 바꿨나 (diff 요약)
- dev 점수: 변경 전 → 변경 후
- 유형별 실패 수: 변경 전 → 변경 후 (전 유형)
- 예상하지 않은 유형이 나빠졌으면 표시
- D 트랙 제안이 있으면 함께
```

## 트랙별 규칙

공통 프롬프트의 `변경 내용`과 `허용 파일`에 트랙별 제약을 넣는다.

### P — 프롬프트

```
- 한 번에 한 가지 지시만 더하거나 고친다
- 기존 지시를 지울 때는 어느 회차가 왜 넣었는지 루프 기록에서
  확인하고 근거를 남긴다
- 프롬프트 총 길이가 <상한>을 넘으면 적용하지 말고 보고한다
```

지시가 쌓이면 서로 충돌한다. 상한이 없으면 루프는 계속 쌓는다.

> 자동화 대안: 지시문 자동 최적화(GEPA 계열)로 이 트랙을 대체할 수 있다. 그 경우 **평가가 스칼라 점수만이 아니라 실패 사유를 문장으로** 내야 한다.

### F — few-shot

```
- 예제 추가/교체와 검색 방식 변경을 같은 회차에 하지 않는다
- 추가하는 예제가 holdout 케이스에서 유래하지 않았는지 확인하고
  확인 결과를 보고에 포함한다
- 예제 수가 <상한>을 넘으면 적용하지 말고 보고한다
```

**두 번째 항목이 이 트랙의 유일하고 치명적인 사고 경로다.** holdout이 few-shot으로 새어 들어가면 게이트가 자기 답을 보고 채점하게 되고, 그 시점부터 모든 회차의 holdout 점수가 무의미해진다.

> 자동화 대안: 추론 시점 예제 검색(KNN 기반 few-shot 선택)을 쓰면 이 트랙이 상시 자동화된다. 그때 F 트랙의 일은 "예제를 고르는 것"이 아니라 **"예제 뱅크에 무엇을 넣을지"**가 된다.

### C — 코드

```
- 동작을 보존해야 하는 수정이면 codex/03의 절차를 따른다
- 동작을 바꾸는 수정이면 codex/02의 절차를 따른다
- 어느 쪽인지 먼저 판정하고 보고한다
```

여기서 새로 정할 것은 없다. 트랙 배정과 게이트만 이 설계를 따르고, 실행 절차는 [02](../../02-aorr-worker-verifier-loop/) 또는 [03](../../03-behavior-preserving-refactor/)을 쓴다.

### D — 데이터 (루프 밖)

**이 트랙은 4단계에서 실행하지 않는다.** 에이전트는 제안만 하고, 아래 절차는 사람이 연다.

```
1. 에이전트의 D 트랙 제안을 모은다 (케이스 ID, 근거)
2. 사람이 원 근거로 판정한다 — 스펙, 도메인 규칙, 실제 사용자 기대
   에이전트의 근거를 그대로 채택하지 않는다
3. 승인된 것만 골든셋을 고친다. 이때만 동결을 연다
4. 이전 회차의 점수를 전부 무효화하고 새 기준으로 재평가한다
5. 루프 기록에 "기준 변경 회차"로 남긴다. 회차 번호를 건너뛰지 말고
   기준 변경임을 표시한다
```

**4번이 빠지면 회차 간 점수 비교가 깨진다.** 기준이 바뀐 시점 전후의 점수는 다른 단위다. 대시보드에서 한 선으로 이으면 안 된다.

## 주의

`점수가 안 오른다고 다른 변경을 시도하는 것` 금지가 실전에서 가장 자주 깨진다. 에이전트는 1회 적용 후 점수가 그대로면 다른 방법을 시도하려 한다. 그러면 **여러 변경이 한 회차에 섞이고 귀속이 사라진다.**

안 올랐으면 그 자체가 이번 회차의 결과다. 5단계에서 되돌리고, 3단계로 돌아가 트랙을 재배정한다.

3번에서 **총점만 보고하지 못하게 한 것**은 상쇄 때문이다. 한 유형을 3건 고치고 다른 유형을 3건 망가뜨리면 총점은 그대로다.
