# 5 · 게이트 — 예제

회차 4. dev +1.3, T2가 2건 퇴행한 상태에서 판정한다.

## 프롬프트

```
[5 - 게이트 · 회차 4]

Gatekeeper가 단독으로 수행한다. 이 단계에서 코드·프롬프트·데이터를
수정하지 않는다.

기준선:
- 기준선 커밋: 7b3e19f
- 직전 통과 회차: 3 / 커밋 e04c72b
- 골든셋 경로: eval/golden/
- 평가 명령(dev): python -m eval.run --set dev --seed 42
- 평가 명령(holdout): python -m eval.run --set holdout --seed 42
- 직전 통과 회차 점수: dev 88.6 / holdout 84.9
- 최소 개선폭: 1.5

이번 회차 계획: docs/loop-log.md의 회차 4 항목
대상 유형: T4
허용 파일: src/kbs/retriever.py, config/kbs.yaml
예상 퇴행 유형: T2, T6

순서대로 확인한다. 앞의 것이 실패하면 뒤를 실행하지 않는다.

1. 동결 확인
   git diff 7b3e19f HEAD -- eval/golden/ eval/judge_rubric.md eval/scoring.py
   비어 있어야 한다. 비어 있지 않으면 즉시 실패로 판정하고 멈춘다.

2. 범위 확인
   git diff --stat e04c72b HEAD
   허용 파일 밖이 변경됐으면 실패로 판정한다.

3. dev 판정
   - 대상 유형(T4)의 실패 수가 줄었나
   - 개선폭이 1.5 이상인가
   - 대상 외 유형이 나빠졌나 — 나빠졌다면 예상 퇴행 목록(T2, T6)에 있나

4. holdout 판정   ← 여기서 처음 연다
   holdout 평가를 실행한다. 총점과 유형별 집계만 본다.
   개별 케이스를 열지 않는다.
   - 총점이 84.9 대비 1.5 이상 떨어지지 않았나

5. holdout 개봉 기록
   docs/loop-log.md의 개봉 카운터를 +1 한다.

판정:
- 1~4를 모두 통과 → 채택 후보. 사람 승인으로 올린다
- 하나라도 실패 → 되돌리기를 제안한다:
    git reset --hard e04c72b
  고쳐서 통과시키자고 제안하지 마.

보고 형식:
| 확인 | 결과 | 근거 |
5개 항목 각각에 통과/실패와 수치를 적는다.

사람 승인에 올릴 것 (통과 시):
- 무엇을 고쳤나
- 점수가 어떻게 움직였나 (dev/holdout, 유형별)
- 이 변경이 다음 회차를 방해하지 않는 이유
- 트레이드오프가 있으면 무엇인가
```

## 나온 판정

| 확인 | 결과 | 근거 |
|---|---|---|
| 1 동결 | 통과 | diff 비어 있음 |
| 2 범위 | 통과 | `config/kbs.yaml` 1파일 3줄. 허용 목록 안 |
| 3 dev | **실패** | 아래 |
| 4 holdout | 실행 안 함 | 3번 실패로 중단 |
| 5 개봉 기록 | — | 열지 않음. 카운터 유지 (3회) |

### 3번 상세

| 조건 | 값 | 판정 |
|---|---|---|
| T4 실패 수 | 8 → 2 | 통과 |
| 개선폭 | +1.3 | **실패** (최소 1.5 미달) |
| 대상 외 퇴행 | T2 7 → 9 | 예상 목록에 있음 → 트레이드오프 |

**개선폭 1.3이 최소 개선폭 1.5에 미달한다.** 2단계에서 측정한 실행 편차가 0.7이므로, 1.3의 상승은 편차 범위 안에 들어갈 수 있다.

> 제안: `git reset --hard e04c72b`로 되돌린다.

### Gatekeeper의 추가 소견

T4가 8 → 2로 크게 줄었는데 총점이 1.3밖에 안 오른 것은 T2 퇴행(7 → 9)이 상쇄했기 때문이다. **개입 자체는 대상 유형에 효과가 있었다.** 실패한 것은 변경의 순효과다.

되돌린 뒤 3단계에서 재설계할 때 참고할 것: 톤 필터를 전역으로 걸지 말고 문의 유형별로 거는 안이 있다. 다만 그건 새 회차의 계획이지 이번 회차를 고칠 방법이 아니다.

## 사람 판정

되돌리기 승인. 회차 4를 `되돌림`으로 기록하고 회차 5에서 재설계한다.

```
회차 4 | F | T4-kbs-example-tone-mixed | 되돌림
  dev 88.6 → 89.9 (+1.3, 최소 개선폭 미달)
  T4 8→2, T2 7→9 (예상된 트레이드오프)
  holdout 열지 않음
  다음: 톤 필터를 전역이 아니라 문의 유형별로 거는 안
```

## 이 예제에서 볼 것

**점수가 올랐는데 되돌렸다.** 이게 최소 개선폭을 정해둔 이유다. 편차 0.7인 평가에서 +1.3을 개선으로 채택하면, 루프는 노이즈를 쌓으면서 회차를 소모한다. 되돌리는 비용이 훨씬 싸다.

**3번에서 멈춰서 holdout을 열지 않은 것**이 순서 규칙의 값어치다. 어차피 되돌릴 변경에 holdout 개봉 1회를 쓰지 않았다. 개봉 횟수는 유한한 자원처럼 다뤄야 한다.

**T2 퇴행이 예상 목록에 있어서 "실패"가 아니라 "트레이드오프"로 분류된 것**에 주목할 것. 목록에 없었다면 판정이 달라진다 — 계획 범위를 넘은 변경이 되고, 개선폭과 무관하게 되돌릴 사유가 된다.

**Gatekeeper가 "개입 자체는 효과가 있었다"를 분리해서 기록한 것**이 다음 회차의 입력이 된다. 이게 없으면 회차 5에서 "T4는 F 트랙으로 안 된다"로 잘못 읽는다. 실제로는 트랙이 맞았고 적용 범위가 넓었을 뿐이다.
