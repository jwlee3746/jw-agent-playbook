# 1 · 에러 분석 — 템플릿

**이 단계는 사람이 한다.** 아래 프롬프트는 에이전트에게 일을 맡기는 것이 아니라, 사람이 읽은 결과를 정리하고 대조하는 데 쓴다.

## 왜 사람이 하나

에이전트에게 실패 트레이스를 요약시키면 **이미 이름이 붙은 유형으로 수렴한다.** 새 유형은 아직 이름이 없어서 요약에서 사라진다. 이 단계의 목적이 정확히 그 새 유형을 찾는 것이라, 여기서 자동화하면 루프 전체가 기존 지표 안에 갇힌다.

사람이 하는 부분:

```
실패 트레이스 100건 이상을 직접 읽는다
  → 자유 서술로 메모한다 (open coding) — 분류하려 하지 말고 본 것을 적는다
  → 메모를 유형으로 묶는다 (axial coding)
  → 새 유형이 안 나올 때까지 트레이스를 더 읽는다
```

## 프롬프트 — 정리와 대조

사람이 메모를 끝낸 뒤에 쓴다.

```
[1 - 에러 분석 · 정리]

내 실패 메모: <메모 파일 경로>
평가 정의: <평가 코드·설정 경로>
실패 트레이스: <트레이스 경로>

1. 메모를 실패 유형으로 묶고 다음 표를 만들어:
   유형 ID | 설명 | 빈도 | 현재 평가가 잡나 | 예상 트랙 | 예시 케이스 3건

2. "현재 평가가 잡나" 칸은 추정하지 마. 평가 정의를 읽고,
   그 유형의 실패가 실제로 점수를 깎는지 코드에서 확인해.
   확인할 수 없으면 [사람 확인 필요]로 둬.

3. 예상 트랙은 다음 기준으로 배정해:
   P 프롬프트 — 지시는 이해했으나 형식·톤·우선순위가 어긋남
   F few-shot — 드문 케이스에서만 틀림. 비슷한 사례를 보여주면 맞힘
   C 코드    — 파싱 실패, 툴 인자 오류, 라우팅 오류, 타임아웃
   D 데이터  — 기대값이 실제로 틀렸거나 모호함

4. 내 메모에는 없지만 트레이스에서 보이는 유형이 있으면 따로 적어.
   단, 메모의 유형과 합치지 말고 "추가 후보"로 분리해.

5. 다음 두 수치를 보고해:
   - 전체 실패 중 "현재 평가가 잡나 = 아니오"의 비율
   - 유형별 빈도 분포

6. 상태를 ROUTING_DECISION_REQUIRED로 두고 멈춰.
   루프를 켤지 말지는 네가 정하지 않는다.
   사람에게 다음을 제시하고 멈춰:
   - 평가가 못 잡는 실패 비율
   - 못 잡는 유형 목록과, 각각을 평가에 넣으려면 무엇이 필요한지
   - 네 권고 (켠다 / 평가를 먼저 고친다)와 그 근거

결과를 <분류표 파일>에 저장하고, 상태를 <루프 기록>에 남겨.

루프를 시작하지 마. 프롬프트·코드·데이터를 수정하지 마.
2단계로 넘어가지 마.
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<메모 파일 경로>` | 사람이 쓴 open coding 메모 |
| `<평가 정의 경로>` | 채점 코드, judge 프롬프트, rubric |
| `<트레이스 경로>` | 실패 케이스의 입력·출력·툴 호출 기록 |
| `<분류표 파일>` | 루프 내내 참조할 산출물 |

## 주의

**4번이 이 프롬프트의 안전장치다.** 에이전트가 찾은 유형을 사람 메모와 합치면 어느 쪽이 사람이 본 것인지 사라진다. 분리해두면 나중에 "에이전트가 놓치는 유형이 무엇인가"를 알 수 있다.

## 루프를 켜도 되나

5번의 첫 수치가 판정 기준이다.

| 평가가 못 잡는 실패 비율 | 판단 |
|---|---|
| 낮다 | 루프를 켠다 |
| 높다 | **평가를 먼저 고친다.** 루프는 안 보이는 실패를 못 고치고, 대신 보이는 것에 과적합한다 |

경계값은 도메인에 따라 다르므로 숫자로 못박지 않는다. 다만 **높은데 켜는 것**이 이 설계에서 가장 비싼 실수다. 회차를 수십 번 돌리고 나서 지표만 오른 것을 알게 된다.
