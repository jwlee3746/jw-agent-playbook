- 평가 명령(dev): python -m eval.run --set dev --seed 42
- 평가 명령(holdout): python -m eval.run --set holdout --seed 42 — 5단계에서만 실행

이번 회차 계획: docs/loop-log.md의 회차 4 항목

허용 파일: src/kbs/retriever.py, config/kbs.yaml

  이번 회차는 검색 방식만 바꾼다

  확인 결과를 보고에 포함한다

## 나온 보고

### 변경

```diff
 config/kbs.yaml
+retrieval:
+  filters:
+    tone: formal
```

`src/kbs/retriever.py`는 이미 필터를 지원해서 수정하지 않았다.

### 점수

```
dev 88.6 → 89.9  (+1.3)
```

### 유형별

| 유형 | 회차 3 | 회차 4 | 변화 |
|---|---|---|---|
| T4 | 8 | 2 | **↓ 6** |
| T1 | 3 | 3 | — |
| T2 | 7 | 9 | **↑ 2** |
| T3 | 0 | 0 | — |
| T5 | 5 | 5 | — |
| T6 | 4 | 4 | — |
| A1 | 3 | 3 | — |

**T2가 2건 나빠졌다.** 3단계 계획의 `나빠질 수 있는 유형`에 T2가 적혀 있었다 — 부분 환불 사례 중 캐주얼 톤이 많아 검색에서 빠질 수 있다고 예상한 그대로다.

확인해보니 부분 환불 계산을 정확히 보여주는 예제 4건 중 3건이 `tone: casual`이라 필터에서 제외됐다.

### holdout 유래 확인

검색 대상 예제 뱅크 342건의 출처를 확인했다. 전부 2026-03 이전 실제 상담 로그이고, `eval/splits/holdout.txt`의 케이스 ID와 겹치는 것은 없다. **holdout 유래 예제 0건.**

### 보고에 함께 올라온 것

> `src/kbs/retriever.py`의 임베딩 캐시가 매 호출마다 재생성된다. 지연의 상당 부분이 여기서 나오는 것으로 보이지만 이번 회차 계획에 없으므로 손대지 않았다.

## 이 예제에서 볼 것

**점수는 올랐는데(+1.3) 다른 유형이 나빠졌다.** 총점만 봤다면 통과였을 것이다. 그리고 +1.3은 최소 개선폭 1.5에도 못 미친다 — 5단계에서 이 두 가지가 판정 대상이 된다.

**T2 퇴행이 3단계에서 이미 예상됐다는 게 중요하다.** 예상된 퇴행이므로 "계획 범위를 넘었다"는 신호는 아니고, 대신 **이 변경 자체가 트레이드오프**라는 뜻이다. 톤을 통일하면 계산 예제를 잃는다. 이건 게이트가 아니라 설계 판단이 필요한 지점이다.

**holdout 유래 확인을 수치로 보고한 것**이 F 트랙의 필수 절차다. "확인했습니다"가 아니라 뱅크 342건 대조 결과 0건이라고 적혀야 나중에 검증된다.

**D 트랙 제안을 실행하지 않은 것**이 규칙대로다. 근거로 정책 문서 조항까지 제시했지만, 그래도 골든셋은 건드리지 않았다. 사람이 판정할 재료를 갖춘 상태로 넘긴다.

**임베딩 캐시 문제를 보고만 한 것**도 규칙대로다. C 트랙 항목으로 분류표에 올린 뒤 별도 회차로 돈다.
