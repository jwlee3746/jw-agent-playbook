# 3 · 실패 라우팅 — 템플릿

이번 회차에 **무엇 하나를 고칠지** 정한다. 아직 고치지 않는다.

## 프롬프트

```
[3 - 실패 라우팅 · 회차 <N>]

기준선:
- 기준선 커밋: <SHA>
- 직전 통과 회차: <N-1> / 커밋 <SHA>
- 골든셋 경로: <골든셋 경로> — 동결. 읽기만 한다
- 평가 명령(dev): <dev 명령>
- 평가 명령(holdout): <holdout 명령> — 5단계에서만 실행
- 현재 점수: dev <값> / holdout <값>
- 최소 개선폭: <값>

읽을 것: <루프 기록>, <분류표 파일>, 직전 회차 dev 평가 결과

1. 현재 dev 실패를 유형별로 집계해. 직전 회차와 비교해서
   늘어난 유형이 있으면 표시해.

2. 이번 회차 대상 하나를 골라. 기준:
   - 빈도 x 영향이 큰 것
   - 같은 지문으로 3회 이상 개입한 유형은 제외 (트랙 재배정 대상)
   - holdout 3건 미만 유형은 제외 (게이트에서 판정 불가)

3. 트랙을 배정해:
   P 프롬프트 — 지시는 이해했으나 형식·톤·우선순위가 어긋남
   F few-shot — 드문 케이스에서만 틀림. 비슷한 사례를 보여주면 맞힘
   C 코드    — 파싱 실패, 툴 인자 오류, 라우팅 오류, 타임아웃
   D 데이터  — 기대값이 실제로 틀렸거나 모호함

   배정 근거를 실패 트레이스에서 인용해. 추정하지 마.
   트랙이 애매하면 두 후보와 각각의 근거를 제시하고 멈춰.

4. 실패 지문을 찍어. 같은 원인의 실패를 묶는 짧은 식별자다.
   형식: <유형ID>-<원인 요약 슬러그>
   기존 지문과 같으면 새로 만들지 말고 기존 것을 쓰고
   개입 횟수를 +1 해.

5. 이번 회차 계획을 보고해:
   대상 유형 | 트랙 | 지문 | 개입 횟수 | 무엇을 바꿀 것인가 |
   예상 영향 범위 | 이 변경이 나빠지게 할 수 있는 다른 유형

결과를 <루프 기록>에 회차 <N> 항목으로 추가해.

아무것도 수정하지 마. holdout 평가를 실행하지 마.
이 단계는 대상 선정까지만이다.
```

## 주의

**한 회차에 대상 하나, 트랙 하나다.** 두 개를 같이 바꾸면 점수가 움직였을 때 무엇이 움직였는지 귀속되지 않고, 다음 회차의 대상 선정이 틀린 전제 위에서 이뤄진다.

3번에서 **트랙이 애매하면 멈추게 한 것**이 중요하다. 에이전트는 애매해도 하나를 골라 진행하는 쪽을 택한다. 트랙 배정이 틀리면 개입은 실패하고, 그 실패가 "이 유형은 고치기 어렵다"로 잘못 기록된다. 실제로는 트랙만 틀렸을 뿐이다.

### 지문이 하는 일

[02의 fingerprint](../../02-aorr-worker-verifier-loop/README.md#실패-기록-필드)와 같다. 같은 유형에 반복 개입하는 것을 **기계가 세게** 한다.

| 개입 횟수 | 뜻 |
|---|---|
| 1~2 | 정상 |
| 3 이상 | **트랙 배정이 틀렸다.** 대개 P로 고치려던 것이 실은 C나 D다 |

사람이 "비슷한 실패 같은데"라고 기억에 의존하면 회차가 쌓일수록 놓친다.

### 마지막 칸

`이 변경이 나빠지게 할 수 있는 다른 유형`을 미리 적게 하는 이유는 5단계 게이트 때문이다. 예상에 없던 유형이 나빠졌다면 **변경이 계획한 범위를 넘었다는 신호**이고, 그건 되돌릴 근거가 된다. [03의 "깨뜨릴 수 있는 테스트"](../../03-behavior-preserving-refactor/prompts/03-change-classification.md)와 같은 장치다.
