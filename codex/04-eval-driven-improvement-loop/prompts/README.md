# 단계별 프롬프트

각 단계에 넘기는 지시문이다. 단계마다 **템플릿**과 **예제** 두 파일이 있다.

- 템플릿(`NN-*.md`) — `<...>` 자리를 채워 쓰는 골격
- 예제(`NN-*.example.md`) — 같은 골격을 실제로 채운 것

예제는 전부 같은 가상 프로젝트를 쓴다: **고객 문의 처리 에이전트 플랫폼.** 평가 파이프라인이 케이스 200건에 대해 툴 호출 정확도와 응답 품질(LLM judge)을 낸다. 과거 처리 사례가 KBS에 쌓여 있고 few-shot으로 검색해 쓴다.

| 단계 | 템플릿 | 예제 | 국면 |
|---|---|---|---|
| 1 에러 분석 | [01-error-analysis.md](01-error-analysis.md) | [예제](01-error-analysis.example.md) | A 기준선 |
| 2 분할과 동결 | [02-freeze-and-split.md](02-freeze-and-split.md) | [예제](02-freeze-and-split.example.md) | A 기준선 |
| 3 실패 라우팅 | [03-failure-routing.md](03-failure-routing.md) | [예제](03-failure-routing.example.md) | B 루프 |
| 4 개입 실행 | [04-intervention.md](04-intervention.md) | [예제](04-intervention.example.md) | B 루프 |
| 5 게이트 | [05-gate.md](05-gate.md) | [예제](05-gate.example.md) | B 루프 |
| 6 회차 감사 | [06-round-audit.md](06-round-audit.md) | [예제](06-round-audit.example.md) | C 감사 |

1·2단계는 최초 1회, 3~5는 회차마다, 6은 N회차마다 돈다.

## 공통 골격

[02](../../02-aorr-worker-verifier-loop/prompts/README.md)·[03](../../03-behavior-preserving-refactor/prompts/README.md)과 같은 골격에 **기준선 칸**이 붙는다. 03과 다른 것은 동결 대상이 테스트가 아니라 골든셋이라는 점, 그리고 **holdout을 열었는지**가 매번 기록된다는 점이다.

```
[<단계 번호> - <단계 이름> · 회차 <N>]

<읽을 것: 루프 기록, 앞 회차 결과, 실패 분류표>

기준선:
- 기준선 커밋: <SHA>
- 직전 통과 회차: <N-1> / 커밋 <SHA>      ← 되돌아갈 지점
- 골든셋 경로: <경로> — 동결. 읽기만 한다
- 평가 명령(dev): <명령>
- 평가 명령(holdout): <명령> — 5단계에서만 실행
- 현재 점수: dev <값> / holdout <값>

역할:
- Worker(<하네스>): <담당>
- Gatekeeper(<하네스>): <담당>

실행 순서:
1. ...

규칙:
- <금지 사항>

멈추는 조건:
- <이 단계에서 사람 판단이 필요한 상황>
- 그때 상태를 <상태 이름>으로 두고 멈춘다
- 사람에게 줄 것: <판단에 필요한 재료>

최종 보고:
- <무엇을 보고할지>
- holdout을 열었으면 그 사실과 이유

<이 단계에서 하지 말 것>
```

**`평가 명령(holdout)`을 3·4단계 프롬프트에도 적어두되 "5단계에서만 실행"을 함께 적는다.** 명령을 감추면 에이전트가 다른 경로로 찾아서 돌린다. 있는 것을 알려주고 언제 쓰는지를 못박는 편이 낫다.

## 멈추는 지점

**`멈추는 조건` 칸을 비워두지 않는다.** 여섯 단계 전부에 사람 판단 지점이 있다.

| 단계 | 상태 | 사람이 결정하는 것 |
|---|---|---|
| 1 | `ROUTING_DECISION_REQUIRED` | 루프를 켤지, 평가를 먼저 고칠지 |
| 2 | — | 최소 개선폭 확정, 종료 조건(Acceptance) 지정 |
| 3 | `TRACK_DECISION_REQUIRED` | 트랙 후보 둘 중 어느 것인지 (애매할 때만) |
| 4 | `DATA_APPROVAL_REQUIRED` | 골든셋을 고칠지 (D 트랙일 때만) |
| 5 | `ROUND_APPROVAL_REQUIRED` | 이번 회차를 채택할지 |
| 6 | `AUDIT_DECISION_REQUIRED` | 계속 / 1단계 복귀 / 종료 |

이름을 붙이는 이유는 [02](../../02-aorr-worker-verifier-loop/README.md#상태)와 같다. **"사람에게 물어봐"는 기록에 남지 않고, 상태 이름은 남는다.** 어느 상태로 몇 번 멈췄는지가 쌓여야 어디서 시간이 갔는지 셀 수 있다.

2단계에만 상태 이름이 없는 것은 루프가 아직 시작되지 않아서다. 대신 그 두 값이 정해지기 전에는 3단계로 넘어가지 않는다 — **최소 개선폭 없이는 게이트가 성립하지 않고, 종료 조건 없이는 루프가 끝나지 않는다.**

## 반복되는 문구와 그 이유

| 문구 | 막는 것 |
|---|---|
| "골든셋·기대값·rubric을 읽기만 하고 수정하지 마" | 기준을 고쳐서 점수를 올리는 것 |
| "이번 회차는 트랙 `<X>` 하나, 변경 하나" | 무엇이 점수를 올렸는지 귀속되지 않는 것 |
| "holdout은 5단계에서만, 총점과 유형별 집계만 본다" | holdout이 회차를 거쳐 dev가 되는 것 |
| "few-shot에 넣을 예제가 holdout에서 온 것이 아닌지 확인해" | 게이트가 자기 답을 보고 채점하는 것 |
| "게이트 실패는 되돌리기다. 통과할 때까지 고치지 마" | 게이트를 목표로 최적화하는 것 |
| "기대값이 틀렸다고 판단되면 고치지 말고 D 트랙으로 제안만 해" | 에이전트가 가장 싼 경로를 택하는 것 |
| "대상 유형 외의 유형이 나빠졌는지 함께 보고해" | 총점 뒤에 상쇄되어 숨는 퇴행 |
| "상태를 `<이름>`으로 두고 멈춰. 네가 정하지 않는다" | 판단이 필요한 지점을 에이전트가 넘어가는 것 |
| "권고만 한다" | 권고가 결정으로 굳는 것 |
| "확인되지 않은 내용은 `[사람 확인 필요]`" | 지어낸 사실이 이후 회차에 퍼지는 것 |
