# 04 · 평가 기반 개선 루프

**한 줄**: 평가 결과를 신호로 에이전트가 프롬프트·few-shot·코드를 고치고, 골든셋은 동결한 채 holdout으로 게이트를 건다.
**출처**: 자작 — 외부 자료를 종합했다. 근거는 [참고](#참고)에 링크와 발췌로 둔다
**상태**: 미검증
**포팅**: [claude/04](../../claude/04-eval-driven-improvement-loop/)

## 용도

**평가 파이프라인이 이미 있는** LLM 에이전트 플랫폼에서, 평가가 뱉은 실패를 개선으로 되먹이는 루프를 돌릴 때 쓴다.

쓰면 안 되는 경우:

| 상황 | 왜 |
|---|---|
| **평가 세트가 실패를 대표하지 못한다** | 루프는 평가가 보는 것만 고친다. 안 보이는 실패는 회차를 아무리 돌려도 안 잡히고, 대신 보이는 것에 과적합된다. 1단계가 이걸 먼저 확인한다 |
| **holdout을 뗄 만큼 케이스가 없다** | 게이트가 성립하지 않는다. 루프가 본 데이터로 판정하면 점수는 항상 오른다 |
| **에이전트 동작을 바꾸는 게 목적이 아니다** | 기능 추가는 [02](../02-aorr-worker-verifier-loop/), 구조 정리는 [03](../03-behavior-preserving-refactor/) |

## 전제

- 하네스 / 모델: 파일 수정 에이전트. 게이트 판정은 별도 주체
- 필요한 툴·권한: 평가 실행 명령, 케이스별 결과를 파일로 내보내는 경로, git
- 레포·환경 조건: **평가가 재현 가능해야 한다.** 같은 입력에 같은 점수가 나오지 않으면 게이트가 노이즈를 개선으로 읽는다. 샘플링 온도·시드·모델 버전을 고정할 수 있어야 한다

## 이 설계의 중심축

### 개입을 네 트랙으로 가른다

실패 하나를 고칠 때, **무엇을 고치는지**에 따라 규칙이 다르다.

| 트랙 | 무엇을 고치나 | 평가가 판정할 수 있나 | 루프 안 |
|---|---|---|---|
| **P** 프롬프트 | 지시문, 역할, 출력 형식 | 예 | 예 |
| **F** few-shot | 검색되는 예제 집합 (KBS 등) | 예 | 예 |
| **C** 코드 | 파이프라인, 툴 정의, 파싱, 라우팅 | 예 | 예 |
| **D** 데이터 | 골든셋의 라벨·기대값·케이스 | **아니오** | **아니오** |

P·F·C는 **시스템**을 고친다. 시스템이 바뀌었으니 같은 기준으로 재면 개선 여부가 나온다.

D는 **기준**을 고친다. 기준을 고치고 그 기준으로 재면 점수는 언제나 오른다. 그래서 D는 루프에서 빼고 별도 절차(사람 승인 + 이전 회차 전량 재평가)로 돌린다. 자세한 것은 [4단계](#4-개입-실행)에 있다.

이 구분이 무너지면 루프 전체가 무의미해진다. **에이전트에게 "점수를 올려라"라고 하면 가장 싼 경로는 언제나 기대값을 고치는 것이다.**

### 골든셋 동결

[03의 테스트 동결](../03-behavior-preserving-refactor/README.md)과 같은 장치다. 대상만 다르다.

```
03: 테스트 파일을 동결하고 프로덕션 코드를 고친다
04: 골든셋을 동결하고 시스템(프롬프트·예제·코드)을 고친다
```

프롬프트로 금지하고, 가능하면 권한으로 막는다.

### dev와 holdout을 나눈다

| 세트 | 루프가 보나 | 쓰임 |
|---|---|---|
| **dev** | 예 | 실패를 고르고 개선안을 만든다 |
| **holdout** | **아니오** | 게이트에서만 연다. 회차마다 열지 않는다 |

holdout이 없으면 루프는 dev에 과적합하고, 점수는 오르는데 실제 품질은 그대로인 상태로 수렴한다. **이 설계에서 holdout 없이 돌리는 것은 게이트 없이 돌리는 것과 같다.**

# 국면 A · 기준선

## 1. 에러 분석

**루프를 켜기 전에, 이 평가가 무엇을 못 잡는지 먼저 본다.**

자동 최적화의 한계가 여기 있다. 최적화는 기존 지표를 올릴 뿐 **새로운 실패 유형을 발견하지 못한다.** 평가가 놓치는 실패는 루프가 영원히 못 고치고, 루프는 그 사실을 모른 채 점수만 올린다.

```
실패 트레이스를 100건 이상 직접 읽는다
  → 자유 서술로 메모한다 (open coding)
  → 메모를 실패 유형으로 묶는다 (axial coding)
  → 새 유형이 안 나올 때까지 반복한다
  → 유형별로 현재 평가가 잡는지 대조한다
```

산출물은 **실패 분류표**다.

```
유형 ID | 설명 | 빈도 | 현재 평가가 잡나 | 예상 트랙 | 예시 케이스
```

`현재 평가가 잡나` 칸에 `아니오`가 많으면 **루프를 켜지 말고 평가를 먼저 고친다.** 이 단계의 산출물은 루프의 입력이자 루프를 켤지 말지의 판단 근거다.

이 단계는 사람이 한다. 에이전트에게 트레이스를 요약시키면 이미 알려진 유형으로 수렴하고, 새 유형은 거기서 사라진다.

## 2. 분할과 동결

### 분할

| 세트 | 크기 | 규칙 |
|---|---|---|
| dev | 전체의 60~70% | 루프가 본다 |
| holdout | 전체의 30~40% | **게이트에서만 연다** |

분류표의 실패 유형이 **양쪽에 고르게** 들어가도록 나눈다. 무작위로 나누면 희귀 유형이 한쪽에만 몰린다.

holdout을 열 수 있는 시점을 규칙으로 정한다 — 예: 회차 게이트에서만, 그리고 결과는 통과/실패와 유형별 집계만 본다. **개별 케이스를 열어보면 그 순간부터 holdout이 아니다.**

### 동결

골든셋 경로를 명시하고 쓰기를 막는다.

```
동결 대상: 골든셋 케이스 파일, 기대값, 라벨, judge 채점 기준(rubric)
동결 예외: 없음. D 트랙만 별도 절차로 연다
```

judge의 rubric을 동결 대상에 넣는 것이 자주 빠진다. **rubric은 기준이지 시스템이 아니다.** rubric을 느슨하게 고치면 점수가 오르고, 그건 개선이 아니다.

### 기준선 기록

```
회차 0 | 커밋 SHA | dev 점수 | holdout 점수 | 유형별 실패 수 | 평가 설정(모델·온도·시드)
```

`평가 설정`을 남기는 이유: 모델 버전이 바뀌면 점수가 움직인다. 그 움직임을 개선으로 읽지 않으려면 무엇으로 쟀는지가 남아야 한다.

# 국면 B · 루프

## 3. 실패 라우팅

이번 회차에 **무엇을 고칠지 하나 고른다.**

```
dev 실패를 유형별로 집계
  → 빈도 × 영향으로 정렬
  → 상위 하나를 고른다
  → 트랙을 배정한다 (P / F / C / D)
  → 실패 지문(fingerprint)을 찍는다
```

### 트랙 배정 기준

| 증상 | 트랙 |
|---|---|
| 지시를 이해했으나 형식·톤·우선순위가 어긋남 | P |
| 드문 케이스에서만 틀림. 비슷한 사례를 보여주면 맞힘 | F |
| 파싱 실패, 툴 인자 오류, 라우팅 오류, 타임아웃 | C |
| **기대값이 실제로 틀렸거나 모호함** | D |

**한 회차에 한 트랙, 한 변경이다.** 두 개를 같이 바꾸면 점수가 올랐을 때 무엇이 올렸는지 귀속되지 않고, 다음 회차에 잘못된 방향으로 더 간다.

### 실패 지문

[02의 fingerprint](../02-aorr-worker-verifier-loop/README.md#실패-기록-필드)와 같은 장치다. 같은 유형에 반복 개입하는 것을 기계가 세게 한다. 같은 지문에 3회 이상 개입했는데 안 고쳐지면 **트랙 배정이 틀렸다는 신호**다 — 대개 P로 고치려던 것이 실은 C나 D다.

## 4. 개입 실행

트랙별로 규칙이 다르다.

### P — 프롬프트

- 한 번에 **한 가지 지시**만 더하거나 고친다
- 기존 지시를 지울 때는 왜 지우는지 근거를 남긴다. 과거 회차가 넣은 것일 수 있다
- 프롬프트 길이 상한을 정해둔다. 루프는 방치하면 지시를 계속 쌓고, 쌓인 지시는 서로 충돌한다

> 자동화 대안: 지시문 자동 최적화(GEPA 계열)를 쓸 수 있다. 이때 **평가가 스칼라 점수만이 아니라 실패 사유를 문장으로** 내야 성능이 나온다 ([참고](#참고)).

### F — few-shot

- KBS에서 예제를 **추가**하는 것과 **검색 방식을 바꾸는 것**을 구분한다. 후자는 모든 케이스에 영향을 주므로 별도 회차로 돌린다
- 추가하는 예제가 **holdout 케이스에서 온 것이 아닌지 확인한다.** 이게 이 트랙의 유일하고 치명적인 사고 경로다 — holdout이 few-shot으로 새어 들어가면 게이트가 자기 답을 보고 채점하게 된다
- 예제 수 상한을 정한다. 늘리면 대개 점수가 오르지만 비용과 지연도 오른다

> 자동화 대안: 추론 시점 예제 검색(KNN 기반 few-shot 선택)이 이 트랙을 상시 자동화한다. 그 경우 루프의 F 트랙은 "예제를 고르는 일"이 아니라 "예제 뱅크에 무엇을 넣을지"가 된다.

### C — 코드

파이프라인·툴·파싱 코드를 고친다. **[03](../03-behavior-preserving-refactor/)의 절차를 그대로 쓴다** — 동작 보존이 필요한 구간이면 03이 맞고, 동작을 바꾸는 수정이면 [02](../02-aorr-worker-verifier-loop/)다.

여기서 새로 정할 것은 없다. 트랙 배정과 게이트만 이 설계를 따른다.

### D — 데이터 (루프 밖)

**골든셋을 고치는 유일한 경로다.** 루프에서 빼는 이유는 앞서 말한 대로 — 기준을 고치고 그 기준으로 재면 개선이 측정되지 않는다.

절차:

```
1. 에이전트는 "이 기대값이 틀렸다"를 근거와 함께 제안만 한다. 고치지 않는다
2. 사람이 원 근거(스펙, 도메인 규칙, 실제 사용자 기대)로 판정한다
3. 승인되면 골든셋을 고친다
4. 이전 회차의 점수를 전부 무효화하고 새 기준으로 재평가한다
5. 기준선 기록에 "기준 변경" 회차로 남긴다
```

4번이 빠지면 회차 간 점수 비교가 깨진다. 기준이 바뀐 시점 전후의 점수는 다른 단위다.

**에이전트가 D 트랙을 제안하는 빈도 자체가 지표다.** 자주 나온다면 골든셋 품질에 문제가 있거나, 에이전트가 쉬운 길을 찾고 있는 것이다. 6단계가 이걸 센다.

## 5. 게이트

변경을 적용한 뒤 판정한다. **판정은 변경을 만든 주체가 하지 않는다.**

| 조건 | 기준 |
|---|---|
| dev 개선 | 대상 실패 유형의 실패 수가 줄었다 |
| dev 미퇴행 | **다른 유형이 나빠지지 않았다** |
| **holdout 미퇴행** | holdout 총점이 기준선 대비 떨어지지 않았다 |
| 골든셋 동결 | `git diff`로 골든셋 경로 변경이 0 |
| 변경 범위 | 이번 회차 트랙 밖 파일이 안 바뀌었다 |

하나라도 실패면 **되돌린다.** 고쳐서 통과시키지 않는다 — 게이트를 통과할 때까지 고치는 것은 게이트를 목표로 최적화하는 것이고, 그러면 게이트가 dev의 연장이 된다.

`dev 미퇴행`이 자주 빠진다. 한 유형을 고치면서 다른 유형을 망가뜨리는 개입이 흔하고, 총점만 보면 상쇄되어 안 보인다. **유형별로 본다.**

통과하면 사람 승인으로 올린다. 승인 항목은 셋이다 — 무엇을 고쳤나, 점수가 어떻게 움직였나, **왜 이 변경이 다음 회차를 방해하지 않나.**

# 국면 C · 감사

## 6. 회차 감사

N회차마다(권장 5회) 루프 자체를 점검한다. **개별 회차 게이트가 잡지 못하는 것들이 여기서 잡힌다.**

| 신호 | 무엇을 뜻하나 | 대응 |
|---|---|---|
| **dev–holdout 격차가 회차마다 벌어진다** | dev 과적합 | 루프를 멈추고 dev를 갱신하거나 1단계로 돌아간다 |
| 회차당 개선폭이 계속 줄어든다 | 현재 평가로 짜낼 수 있는 것을 다 짰다 | 1단계(에러 분석)를 다시 돈다. 새 실패 유형을 찾을 시점 |
| 같은 지문에 3회 이상 개입 | 트랙 배정이 틀렸다 | 트랙을 재배정한다. 대개 P → C 또는 D |
| **D 트랙 제안이 잦다** | 골든셋 품질 문제이거나, 에이전트가 쉬운 길을 찾고 있다 | 제안들을 모아 사람이 한 번에 판정 |
| 프롬프트 길이가 계속 는다 | 지시가 쌓여 서로 충돌하는 중 | 프롬프트 정리 회차를 따로 돈다 |
| holdout을 연 횟수가 회차 수에 근접 | holdout이 사실상 dev가 됐다 | 새 holdout을 떼거나 루프를 멈춘다 |

마지막 항목이 조용히 무너지는 경로다. 게이트마다 holdout을 열면 홀드아웃 정보가 회차를 거쳐 루프로 새어 들어간다. **여는 횟수 자체를 센다.**

## 루프가 답하지 못하는 것

여섯 단계를 다 돌아도 남는다.

- 평가에 없는 실패 유형 — 루프는 그 존재를 모른다
- 지표는 올랐는데 사용자 경험은 그대로인 경우
- 여러 개입이 쌓여 만든 복잡도

**루프는 정의된 지표를 올릴 뿐이다. 지표가 옳은지는 1단계와 6단계에서 사람이 판단한다.**

---

## 이 설계의 요점

1. **개입을 네 트랙으로 가르고, 데이터 트랙만 루프 밖에 둔다.** 시스템을 고치는 것과 기준을 고치는 것은 같은 루프에 있을 수 없다.
2. **골든셋과 rubric을 동결한다.** 점수를 올리는 가장 싼 경로를 막는다.
3. **holdout을 게이트에서만 연다.** 여는 횟수를 센다.
4. **한 회차에 한 트랙, 한 변경.** 귀속되지 않으면 다음 회차가 틀린다.
5. **게이트 실패는 되돌리기다.** 통과할 때까지 고치면 게이트가 dev가 된다.
6. **에러 분석은 루프 밖에 있고 사람이 한다.** 루프는 새 실패 유형을 발견하지 못한다.

1번과 2번은 [03](../03-behavior-preserving-refactor/)의 테스트 동결과 같은 원리다. 03은 테스트를, 04는 골든셋을 기준선으로 놓는다. 4번은 [02](../02-aorr-worker-verifier-loop/)의 "원인 하나 최소 수정"과 같다.
