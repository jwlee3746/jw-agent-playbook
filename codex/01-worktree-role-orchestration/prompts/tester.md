# Tester — 템플릿

통합본을 검증하고 증거를 만든다. **코드를 고치지 않는다.** 다섯 역할 중 제약이 가장 많다.

## 프롬프트

```markdown
# <task-id> · Tester 작업 명세

## 작업장
branch `<task-id>-tester`, 시작 branch `<task-id>-integration`.
통합 결과(두 구현의 병합본) 위에서 검증한다.

## 규칙
- **구현 코드를 수정하지 않는다** (<구현 파일 목록>)
- **검증 스크립트와 채점 파일을 수정하지 않는다**
- **통과시키려고 결과를 조작하지 않는다**
- 증거는 `<test 증거 경로>` 아래에만 생성한다

## 시작 확인 (아직 아무것도 바꾸지 않는다)
- branch 생성 시점의 HEAD가 통합 branch의 최신 commit과 같은가
- working tree가 clean한가

## 실행
- `<기능 검증 명령>`
- `<화면 검증 명령>`
- `<권한 감사 명령>`

## 증거 작성
- `<report 경로>`
  - 실제 PASS/FAIL, 위험도, 남은 리스크를 기록
- `<approval draft 경로>`
  - `status` 는 항상 `pending`
  - 모두 통과하면 recommendation 은 `<승인 후보 값>`
  - 하나라도 실패하면 recommendation 은 `<보류 값>`

## 권한
- allowedFiles: <report 경로>, <approval draft 경로>
- forbiddenFiles: <모든 구현 파일>, <데이터 파일>, <검증 스크립트>, <채점 파일>

## 마무리
1. 위 두 파일만 `git add` → `git commit`
2. merge / rebase / push 금지
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<test 증거 경로>` | `docs/<task-id>/test/` 형태로 고정 |
| `<승인 후보 값>` `<보류 값>` | 사람이 읽을 권고 값. 승인 자체가 아니다 |

## 주의

**`status`는 항상 `pending`이다.** 에이전트가 승인 상태를 쓰는 것 자체가 금지다. 권고는 적을 수 있지만 판단은 사람이 한다. 이 한 줄이 없으면 승인 게이트가 형식만 남는다.

**"시작 확인"이 이 역할에만 있다.** 검증자는 자기가 검증하는 대상이 무엇인지 먼저 확정해야 한다. HEAD가 통합본과 다르거나 working tree가 지저분하면, 무엇을 검증한 결과인지 알 수 없다.

**"통과시키려고 결과를 조작하지 않는다"를 명시한다.** 다른 역할에는 없는 문장이다. 검증자에게는 실패를 없애는 가장 쉬운 방법이 결과를 고치는 것이라, 그 경로를 말로 막아둔다.

`allowedFiles`에 구현 파일이 하나도 없다. 검증자가 대상을 고칠 수 있으면 통과의 의미가 사라진다.
