# Backend — 템플릿

서버 로직을 구현해 기능 검증을 통과시킨다. Frontend와 동시에 진행하며 서로 기다리지 않는다.

## 프롬프트

```markdown
# <task-id> · Backend 작업 명세

## 작업장
branch `<task-id>-backend`, 시작 branch `<기준 branch>`.
worktree를 손으로 만들지 않는다(하네스가 관리하는 경우).

## 목표
`<기능 검증 명령>` 을 PASS 시킨다.

## 구현할 것
<어느 파일의 어느 함수·엔드포인트를 완성하는가>
<판정 규칙을 서술>
정확한 기대값은 `<채점 파일>` 의 <케이스 섹션> 을 기준으로 한다.

## 유지할 것
- <기존에 동작하던 엔드포인트·동작>
- <환경 제약: 외부 패키지 금지 등>

## 권한
- allowedFiles: <서버 구현 파일>, <backend report 경로>
- forbiddenFiles: <프론트엔드 파일>, <데이터 파일>, <검증 스크립트>, <채점 파일>
- 다른 역할의 구현 파일에 손대지 않는다

## 중단 조건
<검증 실패가 연속 N회 반복될 때 중단하고 로그를 남긴다>

## 마무리
1. `<기능 검증 명령>` 실행 → PASS 확인
2. `<backend report 경로>` 작성 — 무엇을 왜 바꿨는지, 실행한 명령과 exit code
3. allowedFiles 만 `git add` → `git commit`
4. merge / rebase / push 금지
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<task-id>` | 작업 식별자. branch 이름과 report 경로에 함께 쓴다 |
| `<기능 검증 명령>` | 이 역할의 통과 판정에 쓰는 명령 하나 |
| `<채점 파일>` | 케이스와 권한이 들어 있는 데이터 파일 |
| `<backend report 경로>` | `docs/<task-id>/backend/report.md` 형태로 고정 |

## 주의

**판정 규칙을 서술하더라도 "정확한 기대값은 채점 파일을 따른다"를 반드시 붙인다.** 명세와 채점표가 어긋나면 채점표가 이겨야 한다. 이 문장이 없으면 에이전트가 명세 쪽을 근거로 통과를 주장할 수 있다.

`유지할 것`에 **기존에 동작하던 것**을 적는다. 새로 만드는 것에만 집중하면 멀쩡하던 동작이 부수적으로 깨진다.

`forbiddenFiles`에 검증 스크립트와 채점 파일을 반드시 넣는다. 없으면 통과하지 못할 때 기준을 낮추는 경로가 열린다.
