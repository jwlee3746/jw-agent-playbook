# Integration — 템플릿

두 구현 branch를 합치고 전체 검증을 돌린다. **구현 파일을 고치지 않는다.**

## 프롬프트

```markdown
# <task-id> · Integration 작업 명세

## 작업장
branch `<task-id>-integration`, 시작 branch `<task-id>-backend`.
worktree를 손으로 만들지 않는다(하네스가 관리하는 경우).

## 목표
`<task-id>-frontend` 를 병합하고 전체 검증을 통과시킨다.

## 하는 일
1. `<frontend branch>` 를 `--no-ff` 로 병합한다
2. 전체 검증을 실행한다: `<기능 검증>`, `<화면 검증>`, `<권한 감사>`
3. 결과를 report에 기록한다

## 하지 않는 일
- **구현 파일을 수정하지 않는다.** 검증이 실패하면 해당 역할에게 되돌려 보낸다
- 충돌이 나면 **임의로 해소하지 않고 멈춘다**

## 권한
- allowedFiles: <integration report 경로>
- forbiddenFiles: <모든 구현 파일>, <데이터 파일>, <검증 스크립트>, <채점 파일>

## 중단 조건
- 병합 충돌이 발생하면 즉시 중단하고 충돌 파일과 함께 보고한다
- 검증이 실패하면 원인 분류와 관련 파일을 보고하고 중단한다

## 마무리
1. 세 검증의 결과와 exit code를 기록
2. `<integration report 경로>` 작성 — 병합 대상, 검증 결과, 남은 위험
3. report 만 `git add` → `git commit`
4. push 금지
```

## 채울 것

| 자리 | 무엇을 넣나 |
|---|---|
| `<권한 감사>` | 각 역할의 diff를 허용 파일 목록과 대조하는 명령 |
| `<integration report 경로>` | `docs/<task-id>/integration/report.md` 형태로 고정 |

## 주의

**"충돌이 나면 임의로 해소하지 않는다"가 이 역할의 핵심 제약이다.** 통합 역할이 충돌을 그 자리에서 정리하면 어느 쪽 구현이 살아남았는지 아무도 모르게 된다. 충돌은 두 구현 역할이 같은 곳을 건드렸다는 신호이므로, 그 사실 자체가 보고 대상이다.

**검증 실패도 마찬가지다.** 여기서 고치면 통합 역할이 세 번째 구현자가 되고, 권한 분리가 무너진다.

`--no-ff`를 쓰는 이유는 병합 지점을 커밋으로 남기기 위해서다. fast-forward로 합치면 어느 역할의 작업이 언제 들어왔는지 그래프에서 사라진다.

`allowedFiles`가 report 하나뿐이라는 점이 이 역할의 성격을 그대로 보여준다.
